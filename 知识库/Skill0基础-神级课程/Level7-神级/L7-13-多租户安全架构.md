# L7-13：多租户安全架构 —— 商家A绝不可能看到商家B的订单数据

> 🎯 **学电商平台的安全架构设计**：不是"加个 HTTPS 和 JWT 就是安全了"，而是从认证授权、租户隔离、数据加密、API 安全、支付安全、到攻击防护和安全审计的纵深防御体系。
> ⏱️ **预计时间**：45 分钟

***

> [!tip] 💡 白话小课堂
> 电商安全不只是"加HTTPS和JWT"——那相当于门上装了个好锁但窗户全开着。电商平台比普通SaaS多了至少三层额外风险：多商户数据隔离（商家A不能看到商家B的订单）、真金白银的支付安全（少收一分钱是损失，多收一分钱是事故）、用户隐私合规（手机号、地址、购买记录）。安全不是功能，是持续的过程。

> [!warning] ⚠️ 避坑指南
> IDOR（水平越权）是电商最常见也最危险的安全漏洞——攻击者把URL中的order_id从123改成456，就能看到别人订单。修复方式是在后端每个查询都加上`WHERE tenant_id = current_user.tenant_id`——这不是一次性的修复，而是每个API端点都必须遵守的铁律。另一个高危漏洞：支付金额从请求body中取——攻击者可以改成0.01元买走100元的商品。金额必须从服务端数据库的订单表读取。

> 💡 **白话小课堂**： IDOR 就是"通过改 URL 里的数字去看别人的数据"。

> [!info] 🔑 核心秘诀
> 多租户隔离的混合策略：不同数据用不同隔离级别。商家核心数据（订单、收入、用户）→独立Schema或独立DB（强隔离）；公开数据（商品、评论）→共享表（性能优先）；支付数据→独立DB（最强隔离，PCI DSS合规）。不是全用一种模式——这既控制成本又保证关键数据的安全隔离。

## 1. 电商平台的安全威胁模型

```markdown
## 攻击面分析——电商平台比普通 SaaS 多几层风险

### 攻击面 1: 多租户数据隔离
  → 商家 A 不能看到商家 B 的订单/收入/用户数据
  → 风险：水平越权（IDOR）——修改 URL 中的 store_id
  → 风险：垂直越权——普通店员访问店主的财务数据

### 攻击面 2: 支付安全
  → 涉及真实金钱，是最敏感的攻击目标
  → 风险：支付金额篡改（修改请求中的 amount）
  → 风险：支付回调伪造（假装收到支付成功通知）
  → 风险：退款欺诈（重复退款、超额退款）

### 攻击面 3: 用户数据保护
  → 个人信息：手机号、地址、购买记录
  → 风险：数据泄露（未加密存储、日志泄露）
  → 风险：撞库攻击（用泄露的密码库尝试登录）
  → 合规：GDPR / 个人信息保护法

### 攻击面 4: API 滥用
  → 公开 API 被恶意调用
  → 风险：爬虫（爬取所有商品和价格）
  → 风险：刷单（虚假订单操纵排名）
  → 风险：DDoS（打挂搜索/商品详情页）

### 攻击面 5: 供应链攻击
  → 第三方依赖的漏洞
  → 风险：npm/pip 包被投毒
  → 风险：第三方 SDK（支付/地图/客服）的安全问题
```

## 2. 纵深防御架构

```markdown
## 五层防御体系

### Layer 1: 网络边界（Network）
  → WAF（Web Application Firewall）：SQL 注入、XSS、CSRF
  → DDoS 防护：流量清洗、限流
  → CDN 层安全：HTTPS 强制、HSTS
  → API Gateway：统一鉴权、限流、日志

### Layer 2: 认证与授权（AuthN / AuthZ）
  → 认证（你是谁）：
    - JWT + OAuth 2.0（短期 Access Token + 长期 Refresh Token）
    - 多因素认证（MFA）用于商家后台
    - 防暴力破解：5 次失败 → 锁定 15 分钟
  
  → 授权（你能做什么）：
    - RBAC（角色权限）：店主 / 管理员 / 店员 / 客服
    - 细粒度权限：商品管理、订单管理、财务查看、设置修改
    - 租户隔离：每个查询必须带 tenant_id（不要信任 URL 中的）

### Layer 3: 应用安全（Application）
  → 输入验证：所有输入都不可信
    - 参数类型、范围、格式校验
    - SQL 注入防护（参数化查询）
    - XSS 防护（输出编码）
  
  → 业务逻辑安全：
    - 支付金额验证（后端验签，前端金额不可信）
    - 优惠券使用次数限制（防止并发刷券）
    - 秒杀防刷（一人一单、设备指纹）
  
  → /cso 持续安全审计：
    - OWASP Top 10 检查
    - STRIDE 威胁建模
    - 每次 PR 自动运行

### Layer 4: 数据安全（Data）
  → 传输加密：TLS 1.3
  → 存储加密：
    - 密码：bcrypt（不是 MD5/SHA256）
    - 手机号：AES-256 加密存储
    - 支付信息：不自己存储，用支付网关的 token 化（PCI DSS 合规）
  
  → 日志安全：
    - 不记录敏感字段（密码、手机号、支付信息）
    - 日志脱敏（手机号 138****1234）
    - 日志保留期 + 自动清理

### Layer 5: 监控与响应（Monitoring）
  → 异常检测：
    - 同一用户短时间内大量请求 → 可能是攻击
    - 同一 IP 尝试多个用户登录 → 撞库攻击
    - 异常退款模式 → 退款欺诈
  
  → /guard 运行时防护：
    - 5 层防御（prompt injection / canary / content safety / ML / audit log）
    - 特别是 AI 客服的 prompt injection 防护
  
  → 安全事件响应：
    - 发现异常 → 告警 → On-Call → 止损 → 根因分析 → 修复
    - 安全事件的 Postmortem 和普通故障同样重要
```

## 3. 多租户数据隔离模式

```markdown
## 三种隔离模式——选择取决于业务特征

### 模式 A: 共享数据库 + 共享表（Shared DB + Shared Tables）
  所有租户的数据在同一张表中，用 tenant_id 区分
  
  优点：
    → 成本最低（一套 DB）
    → 运维最简单
    → 新租户零成本
  
  缺点：
    → 隔离性最弱（一个 SQL 忘记加 WHERE tenant_id = ? 就泄漏）
    → 无法为高价值租户提供更好的性能
  
  适用：中小商家，对数据隔离要求不极端

### 模式 B: 共享数据库 + 独立 Schema（Shared DB + Separate Schema）
  每个租户有独立的 Schema（表结构相同，但物理隔离）
  
  优点：
    → 隔离性中等（Schema 级别的权限控制）
    → 可以为部分租户定制扩展字段
  
  缺点：
    → 运维复杂度增加（N 个 Schema 的迁移要同步）
    → 跨租户查询困难
  
  适用：中型以上商家，对数据隔离有一定要求

### 模式 C: 独立数据库（Separate DB）
  每个租户独立数据库
  
  优点：
    → 隔离性最强（物理隔离）
    → 可独立扩容、备份
    → 合规友好（数据可以存放在特定区域）
  
  缺点：
    → 成本最高
    → 运维复杂（N 个数据库的迁移、备份、监控）
    → 跨租户查询需要额外的聚合层
  
  适用：大型商家、金融级隔离要求、合规强需求

### 电商平台的混合策略
  不是全选一种模式——不同数据用不同隔离级别：
    → 商家核心数据（订单、收入、用户）：模式 B 或 C（强隔离）
    → 公开数据（商品、评论）：模式 A（共享，效率优先）
    → 支付数据：模式 C（最强隔离，PCI DSS 合规）
```

## 4. 电商案例：SaaS电商平台多商家数据隔离架构

> 🛒 **实战案例**：某SaaS电商平台在3个月内从50家商家快速增长至500家，但安全建设严重滞后——团队的安全意识停留在"加了HTTPS和JWT就很安全"。直到某天，一个商家在客服群发了一张截图：他在URL中把order_id从自己商家的#12847改成了#12848，竟然看到了竞争对手的订单详情——包括客户姓名、手机号、订单金额。安全恐慌爆发：500家商家中已有3家威胁要退出平台。CTO下令："立即全量安全审计，停止所有功能开发。"
>
> **用 gstack 架构体系进行安全加固**：
> 1. /cso exhaustive 全量审计整个平台（23个微服务、约850个API端点）→ OWASP（OWASP：开放Web应用安全项目）Top 10 + STRIDE（STRIDE：微软威胁建模框架）威胁建模 → 发现12个安全问题：3 CRITICAL + 4 HIGH + 5 MEDIUM
> 2. CRITICAL发现：(1)IDOR水平越权——GET /api/orders/{order_id}只验证用户已登录但未校验order是否属于当前商家→攻击者改URL即可遍历所有商家订单→修复：每个订单查询强制加WHERE tenant_id=current_user.tenant_id（tenant_id从JWT中提取，不用URL参数）；(2)支付金额篡改——POST /api/payment/create直接使用前端传来的amount→攻击者改成0.01元即可¥299商品付1分钱→修复：金额永远从后端数据库订单表读取；(3)JWT Secret硬编码"my-secret-key-2024"在代码+Git历史中→弱密钥可暴力破解→伪造任意商家JWT→修复：环境变量注入+256-bit随机密钥+90天轮换
> 3. HIGH发现：(4)SQL注入（字符串拼接SQL→"...WHERE name LIKE '%" + keyword + "%'"→修复：参数化查询）；(5)敏感信息日志泄露（所有API记录完整request body含密码/手机号→修复：日志脱敏中间件）；(6)CORS配置Access-Control-Allow-Origin:*→修复：明确白名单域名；(7)密码重置Token永不过期+使用后不失效→修复：15分钟过期+一次性使用
> 4. 多租户隔离混合策略设计：商家核心数据（订单/收入/客户）→独立Schema（强隔离）、公开数据（商品/评论）→共享表+tenant_id字段（性能优先）、支付数据→独立DB（PCI DSS合规要求）——不是全用一种模式，而是用数据敏感度决定隔离级别
>
> **效果**：
> - 修复前：12个漏洞（3 CRITICAL + 4 HIGH + 5 MEDIUM），发生过1次实质性数据泄露
> - 修复后（4周）：0漏洞，所有API端点通过租户校验，数据泄露0次
> - /cso纳入CI管道：每次PR自动运行OWASP+STRIDE扫描→第3个月新引入的依赖有2个MEDIUM漏洞在CI阶段就被拦截→从未进入生产
> - 混合隔离策略效果：商家核心数据隔离达到独立Schema级别，成本仅增加15%（vs 全独立DB增加80%成本）；支付数据独立DB满足PCI DSS合规要求
> - 安全文化转变：从"安全团队的事"变成"每次PR自动运行/每个人的事"——安全左移（Shift Left）成功落地
>
> > 🔑 **启示**：电商多租户安全的最大漏洞不是加密算法复杂度不够，而是IDOR（不安全的直接对象引用）——RESTful API中order_id是自增整数，攻击者不需要任何技术就能遍历所有数据。防御铁律：每个数据访问API端点必须在后端强制加tenant_id校验，tenant_id的来源是JWT/Session（服务端认证信息，不可被客户端篡改），而不是URL参数（完全由客户端控制）。混合隔离策略的核心原则：用数据敏感度和合规要求决定隔离级别——订单数据独立Schema，支付数据独立DB，商品评论共享表——一刀切全用独立DB会造成80%的不必要成本。

## 7. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**D** — Git 分支管理策略是所有软件工程的通用问题，不是电商特有的安全风险。电商平台的特有风险：(A) 多商户数据隔离——RESTful API 中 order_id 是连续整数，攻击者改 URL 即可尝试水平越权；(B) 支付安全——涉及真实资金，安全漏洞直接导致财务损失或合规处罚；(C) 用户隐私——手机号、地址、购买记录构成完整用户画像，泄露后果远超普通的邮箱泄露。

**Q2**：漏洞代码：`SELECT * FROM orders WHERE order_id = $1`（只用了 URL 中的 order_id，没有校验该 order 是否属于当前商家）。攻击：商家 A 登录后把 URL 从 /api/orders/100 改成 /api/orders/200 → 看到商家 B 的订单。修复代码：`SELECT * FROM orders WHERE order_id = $1 AND tenant_id = $2`（$2 从当前登录用户的 session/JWT 中提取，不是从 URL 中取的）。核心差异：tenant_id 的信任来源——修复后 tenant_id 来自服务端认证信息（不可被客户端篡改），而非 URL 参数（完全由客户端控制）。为什么不是一次性修复：因为新增一个 API 端点（如 GET /api/orders/{id}/items/{item_id}）时，开发者可能忘记加 AND tenant_id = ? → 新端点又引入 IDOR。所以必须：代码审查强制检查每个数据访问 API 都有租户校验 + /cso 自动扫描所有 API 端点。

**Q3**：**B** — 这是一个真实且极其危险的攻击场景。HTTPS 加密保护传输过程不被窃听或篡改（中间人攻击防护），但无法防止"客户端自己篡改自己的请求"——攻击者就是合法用户（商家 A），他用自己的 JWT 发起请求，但修改了请求 body 中的 amount 参数。HTTPS 加密的是网络层，应用层的数据（HTTP body）来自客户端，永远不可信。正确做法：后端从数据库读取订单表获取真实 amount，前端传来的 amount 仅用于展示对比——如果两者不一致→记录告警（可能是 bug 或攻击）。

**Q4**：(a) 商家核心数据：独立 Schema 或独立 DB（强隔离）——这些数据如果泄露给其他商家是灾难性的（竞争对手看到你的收入、客户列表）。如果平台有 500 家中小商家，独立 Schema 是成本和隔离的平衡；如果平台有大型商家（月 GMV 千万级）→独立 DB 提供最强隔离和独立扩容。(b) 公开数据：共享表 + tenant_id 字段（模式 A）——商品详情和用户评论是公开可见的（任何人都能看到），隔离不是核心需求，查询性能和成本是首要考量。(c) 支付数据：独立 DB（最强隔离）——PCI DSS 合规要求支付数据物理/逻辑隔离，加密存储，且通常不在自己服务器上存储（用支付网关 token 化）。混合策略的本质：用金钱和合规敏感度决定隔离级别，不是一刀切。

**Q5**：(a) 攻击者可发起的攻击：暴力破解弱密钥 → 伪造任意用户的 JWT（篡改 user_id、tenant_id、role）→以任意商家/店主的身份登录→访问所有商家的所有数据→完成水平越权和垂直越权。JWT 是无状态认证，签名是唯一防伪机制——密钥泄露=整个身份认证体系崩溃。(b) 三个要求：环境变量注入（不存代码仓库中，防止泄露到 Git 历史）；256-bit 随机密钥（不是可猜测的字符串如"my-secret-key-2024"）；密钥定期轮换（90 天轮换，有过渡期新旧密钥同时有效）。(c) /cso 纳入 CI 的原因：如果在发布前才跑→安全漏洞已经在 Staging/Production 环境中存在了数天到数周→已经被动暴露。每次 PR 自动运行→安全漏洞在代码合并前就被发现→从未进入共享分支→攻击窗口为零。安全应该左移（Shift Left）。

**Q6**：攻击者穿透路径：Layer 1（网络边界）—— WAF 拦截 SQL 注入和 XSS 的通用攻击模式→如果攻击是业务逻辑级别的（如 IDOR），WAF 可能不拦截。Layer 2（认证授权）—— JWT 验证确认"你是谁"→RBAC 验证"你能做什么"→如果 JWT 签名和租户校验都正确，攻击者以合法身份通过。Layer 3（应用安全）—— 输入验证（参数类型/范围/格式校验）→业务逻辑安全（支付金额后端读取）→/cso 扫描。这里是 IDOR 的关键防线：后端查询必须加 `AND tenant_id = current_user.tenant_id`。如果这一层没做好→攻击者成功访问商家 B 的数据。Layer 4（数据安全）—— 即使攻击者成功读取了数据，如果手机号等敏感字段加密存储（AES-256）→攻击者得到的是密文。传输过程 TLS 加密阻止中间人窃听。Layer 5（监控与响应）—— 异常检测：如果攻击者大量遍历 order_id 尝试 IDOR→监控系统发现"同一商家短时间内访问了不同租户的大量订单"→告警→/guard 运行时拦截。总结：至少需要突破 Layers 2 和 3 才能接触到商家 A 的订单数据。如果 Layer 4 的加密也应用在订单数据上（一般不需要），则还需突破 Layer 4。

（5/6 通过）
</details>
