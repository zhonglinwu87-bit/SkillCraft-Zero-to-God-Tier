# L7-12：超大规模持续部署 —— 每天部署50次而用户完全无感的工程体系

> 🎯 **学超大规模持续部署的工程实践**：不是"装了 CI/CD 就是持续部署"，而是从部署管道设计、变更安全、回滚策略、金丝雀发布、功能开关、到多环境管理和部署协调的完整体系。
> ⏱️ **预计时间**：45 分钟

***

> [!tip] 💡 白话小课堂
> 持续集成(CI)、持续交付(CD)、持续部署(CD)是三个递进的层次：CI=代码合并时自动跑测试，CD=测试通过自动部署到预发环境，CD=预发通过自动部署到生产（无人审批）。大多数人说的"我们做了CI/CD"其实只做到持续交付——生产部署还是需要人工点击。真正的持续部署意味着对自动化体系有极高的信任——每次PR合并后28分钟自动到100%用户，中间经过5层安全检查。

> [!warning] ⚠️ 避坑指南
> 四个部署脚本的经典缺陷：1）不等待健康检查就返回→Pod还在启动中，此时收到流量=502；2）回滚依赖人工记忆版本号→凌晨3点故障时根本记不住上一个版本；3）数据库迁移和代码部署不是原子的→新代码调用新字段但数据库还没加列=报错；4）多个Squad同时部署→5个金丝雀同时跑，根本无法判断哪个导致的问题。

> [!info] 🔑 核心秘诀
> 功能开关（Feature Flag）是持续部署的王牌——代码部署和功能上线解耦。部署可以在凌晨低峰期（减少风险），功能在上午业务高峰期由PM打开开关。遇到问题怎么办？关Feature Flag只需要1秒，而回滚部署需要分钟级。另外，金丝雀发布的最小有效比例是1%——1%的流量足以检测到问题，但最多只影响1%的用户。

## 1. 持续部署的真正含义

```markdown
## 持续集成 != 持续交付 != 持续部署

### Continuous Integration（持续集成）
  含义：代码频繁合并到主分支（每天多次）
  自动做：Build + Unit Tests + Lint
  产出：一个可部署的 artifact
  门禁：CI 通过 → 可以部署（但部署是人工触发的）

### Continuous Delivery（持续交付）
  含义：CI 通过后自动部署到 Staging 环境
  自动做：CI + Staging 部署 + 集成测试 + E2E 测试
  产出：一个"已准备好部署到生产"的 artifact
  门禁：人工审批 → 部署到生产

### Continuous Deployment（持续部署）
  含义：CI 通过后自动部署到生产（无人工审批）
  自动做：CI + E2E + Canary + 自动回滚
  门禁：自动化检查 + 自动回滚（不是人工审批）
  
  关键：持续部署的前提是对自动化有**极高**的信任
```

## 2. 部署安全——如何放心地每天部署 50 次

```markdown
## 五层部署安全网

### Layer 1: 部署前检查（Pre-Deploy Gates）
  每次部署前自动检查：
    → CI 全部通过（Build + Unit + Lint + Typecheck）
    → /qa standard 通过（集成测试 + E2E 测试）
    → /review 无 CRITICAL 未修复
    → /health > 60（代码质量不下降）
    → /cso 无 P0/HIGH 安全漏洞
    → 部署窗口检查（不在封网期）

### Layer 2: 金丝雀发布（Canary）
  先部署到 1-5% 的流量，观察 N 分钟：
    → /canary 监控：错误率、延迟、业务指标
    → 对比基线（上一个版本）
    → 异常 → 自动回滚
    → 正常 → 逐步放量（1% → 5% → 25% → 100%）
    → 每一步中间观察 5-10 分钟

### Layer 3: 功能开关（Feature Flags）
  代码部署 != 功能上线：
    → 代码部署到 100% 的服务器
    → 功能通过 Flag 控制（灰度放量）
    → 关键优势：
      - 部署和上线解耦（部署在凌晨，上线在上午）
      - 出问题 → 关 Flag（秒级），不用回滚部署（分钟级）
      - AB 测试天然支持

### Layer 4: 自动回滚（Auto-Rollback）
  检测到异常时自动回滚：
    → 错误率超过阈值（vs 基线）
    → P99 延迟恶化 > 50%
    → 关键业务指标骤降（下单率、支付率）
    → 自动回滚到上一个已知正常的版本
    → 告警通知 On-Call（但不需要人工操作）

### Layer 5: 部署后验证（Post-Deploy Verification）
  → 冒烟测试（Smoke Test）：部署后立即验证关键路径
  → 关键 API 健康检查：/health, /api/orders, /api/pay
  → 用户反馈监控：客服投诉量、社交媒体
  → 持续监控 30 分钟 → 确认稳定
```

## 3. 多服务部署协调

```markdown
## 微服务世界的部署挑战

### 问题：服务之间有依赖
  例：订单服务 v2 需要支付服务 v2 的新 API
  → 如果先部署订单服务 v2 → 调用支付服务 v1 → API 不存在 → 失败
  → 如果先部署支付服务 v2 → 它是向后兼容的吗？

### 解决方案

**方案 A: API 版本化 + 向后兼容（推荐）**
  部署顺序不重要——新旧版本共存：
    → 支付服务 v2 添加新 API，保留旧 API
    → 订单服务 v2 调用新 API
    → 部署顺序任意
    → 观察 1 周订单服务全部升级后 → 废弃旧 API

**方案 B: 部署编排（复杂场景）**
  当无法做到向后兼容时：
    → /landing-report 显示所有待部署的版本
    → gstack 自动排序：被依赖的先部署
    → 部署一个 → 验证 → 再部署下一个
    → 不重叠部署（避免中间状态）

**方案 C: 合同测试（Consumer-Driven Contracts）**
  服务之间通过合同定义接口：
    → 支付服务发布 API 合同（OpenAPI spec）
    → 订单服务的测试中验证这个合同
    → 任何破坏合同的变更 → 在 CI 阶段就发现 → 不允许部署
```

## 4. 电商案例：从每周2次到每天50次部署无感知

> 🛒 **实战案例**：某电商平台40人团队、23个微服务，部署现状堪称教科书式的反面案例——每周只有周二和周四晚上8点两个部署窗口，每次部署10-20个PR合并在一起，出问题根本不知道是哪个PR导致的。部署日的工程师焦虑氛围浓厚：周三发现bug要等到周四才能修，每次部署前全员紧张——"千万别是我炸了生产"。去年双11后的第一次部署窗口，20个PR打包部署→上线后支付服务大量超时→排查3小时才定位到是某个PR的Redis连接池配置错误→影响约3000笔订单→那天晚上3个工程师熬到凌晨2点。
>
> **用 gstack 架构体系构建持续部署**：
> 1. /plan-eng-review 设计5层部署安全网：(1)部署前检查——CI全部通过+/review无CRITICAL+/qa standard通过+/health>60+/cso无P0 → (2)金丝雀发布——1%流量观察5分钟→5%观察5分钟→25%观察3分钟→100%全量 → (3)功能开关——代码部署≠功能上线，部署在凌晨低峰期，功能在上午由PM打开 → (4)自动回滚——错误率超过基线50%或P99延迟恶化>50%→自动回滚到上一个已知正常版本 → (5)部署后30分钟持续验证
> 2. /review 审查现有deploy.sh → 发现4个CRITICAL：(1)部署脚本无健康检查等待——kubectl apply立即返回但Pod还在启动→收到流量=502→修复：wait_for_rollout()+Pod Ready检查；(2)回滚依赖人工记忆版本号→凌晨3点故障记不住上一个版本→修复：每次部署自动记录deploy_history+/landing-report版本追踪；(3)数据库迁移与代码部署非原子——先部署代码调用新字段但DB还没加列→报错→修复：两步迁移（先加列保持兼容→部署新代码→再删旧列）；(4)无部署频率限制——5个Squad同时部署5个Canary并行→无法判断谁导致问题→修复：/landing-report排队机制（同一时间最多1个部署进行中）
> 3. /skillify 创建"部署后实时监控"Skill → 自动打开Grafana部署监控大盘→对比部署前后5分钟指标（错误率/P99延迟/下单成功率/支付成功率）→异常检测自动回滚或告警→30分钟观察期后生成部署报告
> 4. 8周渐进式改造：Week 1-2搭建CI+测试覆盖率45%→78%/CI时间25min→12min（并行化）→Week 3-4引入Canary+自动回滚（3次部署问题在1%阶段被拦截→0用户影响）→Week 5-6功能开关上线（代码部署和功能上线完全解耦）→Week 7-8部署频率全面放开
>
> **效果**：
> - 部署频率：2次/周→日均50次（每次仅1-3个PR），问题定位精度从"20个PR中找"→"1-3个PR中找"
> - MTTR（平均修复时间）：4小时→12分钟（回滚自动化，无需登录服务器手动操作）
> - 变更失败率：15%→0.3%（5层安全网拦截了大部分问题）
> - 部署导致的P0故障：月均3次→0.2次/月（Canary在1%阶段拦截了97%的问题）
> - 工程师心态转变：部署从"重大事件"变成"例行操作"——部署日焦虑消失，周三的bug不再需要等到周四
> - 典型拦截案例：某次Redis连接池配置错误→之前（全量部署）：100%用户受影响5分钟后才发现；之后（Canary）：1%请求超时→自动检测→自动回滚→仅1%用户受影响2分钟
>
> > 🔑 **启示**：持续部署的速度上限不是你写代码的速度，而是你"有信心在5分钟内发现并回滚任何问题"的能力。功能开关是持续部署的王牌——代码在凌晨2点部署到100%服务器（Flagg关闭状态，用户无感），功能在上午10点由PM打开。出问题怎么办？关Flag需要1秒（回滚部署需要分钟级），且关Flag=PM自主操作（不需要紧急呼叫工程师）。高频小批量部署的原理：每次部署越小→出问题时"二分查找"的范围越精确→部署本质从"高风险赌博"变成"低风险例行操作"。

## 6. 掌握检验

**Q1**：持续集成(CI)、持续交付(CD)、持续部署(CD)三者递进的关键区别是什么？大多数人说的"我们做了 CI/CD"实际上停留在哪个层级？
- A) 大多数人已实现持续部署
- B) 大多数人只做到了持续交付——测试通过后自动部署到 Staging 环境，但生产部署仍需人工审批点击。真正的持续部署意味着 CI 通过后自动部署到生产，无人工审批，依赖自动化检查+自动回滚保证安全
- C) 持续集成和持续部署是一回事
- D) 持续集成就足够了，不需要持续部署

**Q2**：五层部署安全网（部署前检查 / Canary / Feature Flag / 自动回滚 / 部署后验证）中，Feature Flag 相比其他层有一个独特的工程优势——"部署和上线解耦"。请用至少一个具体场景说明：为什么"关 Feature Flag 需要 1 秒，回滚部署需要分钟级"是架构上的巨大差异？如果你的团队今晚凌晨 2 点部署了新代码，Feature Flag 关闭状态——第二天上午 10 点 PM 打开 Flag 后发现严重 bug——对比"没有 Feature Flag 必须回滚部署"的场景，工程师和用户分别体验到了什么差异？

**Q3**：gstack /review 审查部署脚本发现了 4 个 CRITICAL 缺陷。其中"数据库迁移和代码部署不是原子的"——请解释这个问题，并说明正确的两步迁移策略（先加列→部署新代码→再删旧列）为什么能消除风险？
- A) 新代码调用新列 new_status → 但数据库还没执行 ALTER TABLE ADD COLUMN → 所有请求报错。两步策略：先执行只加列不删列的迁移（向后兼容，旧代码忽略新列，新代码可用新列），然后部署新代码，确认稳定后再清理旧列。任何时候数据库和代码之间至少有一个是兼容的
- B) 数据库迁移应该和代码部署同时进行
- C) 使用分布式事务可以解决
- D) 先部署代码，失败后再执行数据库迁移

**Q4**：多服务部署协调中，"API 版本化 + 向后兼容"为什么是推荐的方案？请设计一个具体场景：支付服务 v1 API 返回 `{status, amount}`，v2 需要新增 `{status, amount, currency, exchange_rate}`。如何设计才能让订单服务可以在任意时间升级——先升级支付服务还是先升级订单服务都不影响系统运行？

**Q5**：Canary 金丝雀发布的渐进放量策略（1%→5%→25%→100%）中，每一步的"通过标准"和"观察时间"应该基于什么设定？如果 1% Canary 阶段发现 P99 延迟从基线 200ms 恶化到 500ms，而错误率没有变化——你应该回滚还是继续放量？为什么？

**Q6**：案例中部署频率从每周 2 次变为每天 40 次后，"问题定位精确度"是如何提升的？每周 2 次部署（每次 10-20 个 PR）和每天 40 次部署（每次 1-3 个 PR）——如果上线后发现问题，排查范围有什么数量级差异？

## 7. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** — 三个层级递进：CI（持续集成）= 代码合并到主分支时自动 Build + Unit Tests + Lint，产出可部署 artifact，但部署是人工触发的。CD（持续交付）= CI 通过后自动部署到 Staging + 集成测试 + E2E，产出"准备好上生产"的 artifact，但部署到生产需要人工审批。CD（持续部署）= CI 通过后自动部署到生产，经过 Canary 逐步放量+自动回滚，无任何人工审批环节。关键：持续部署的前提是对自动化有极高的信任——自动化检查体系的误报率和漏报率都必须在可接受范围内。大多数人说的"我们做了 CI/CD"实际是持续交付——因为完全信任自动化到可以无人审批上线是一个巨大的文化和工程飞跃。

**Q2**：Feature Flag 关闭状态下凌晨 2 点部署新代码——代码已在 100% 服务器上运行，但功能被 Flag 关着，对用户完全不可见。上午 10 点 PM 打开 Flag → 发现严重 bug → PM 关闭 Flag（1 秒）→ 功能恢复为 Flag 关闭状态（旧行为），用户在 1 秒后就不再受影响。然后工程师在有充足时间的情况下调查和修复（可以花数小时）。没有 Feature Flag 的对比场景：凌晨 2 点部署→代码在 100% 服务器上直接生效→上午 10 点 PM 发现严重 bug→工程师被紧急叫回→需要找到上一个已知正常的版本→执行回滚部署（pull 旧镜像+等待 Pod 启动+健康检查）→至少 5-10 分钟→期间所有用户持续受影响。差异：关 Flag=秒级，回滚=分钟级；关 Flag=PM 自主操作，回滚=需要工程师；关 Flag=只有 Flag 控制的路径受影响，回滚=整个部署的所有变更被撤回。

**Q3**：**A** — 如果先部署代码：新代码调用 new_status 列→但数据库还没这列→SQL 错误→所有相关请求返回 500。如果先执行数据库迁移：new_status 列已存在但旧代码不查询它→没问题。但迁移还会删除旧列 old_status→旧代码还引用它→SQL 错误。两步策略消除风险：Step 1（先执行）仅添加新列 new_status，不删除旧列→此时数据库有新旧两列→旧代码只用 old_status（不受影响），新代码准备用 new_status→Column 已存在。Step 2 部署新代码→新代码用 new_status→稳定。Step 3（观察后）清理旧列 old_status。任何时候数据库和代码之间至少有一个是兼容的——没有"代码要新列但数据库没有"或"代码要旧列但数据库删了"的时间窗口。

**Q4**：支付服务 v2 新增 currency 和 exchange_rate 字段，同时保留 old_status 和 amount 的兼容性。API 设计：v2 返回 `{status, amount, currency, exchange_rate}`（包含 v1 的所有字段作为子集）。订单服务 v1（调用 v1 API 仅用 status, amount）→可以继续用 v2 服务（因为 v2 返回中包含 status 和 amount）→订单服务完全不需要感知支付服务升级了。订单服务 v2（想用 currency 和 exchange_rate）→升级自己到 v2→调用 v2 API→使用新字段。部署顺序任意：(1) 先部署支付 v2（但保留 v1 兼容）→订单 v1 照常工作→然后订单逐个升级 v2；(2) 先部署订单 v2（调用支付 v1→缺少新字段）→订单 v2 使用默认值 fallback→然后升级支付 v2。等所有消费者（订单服务）都升级到 v2 且稳定一段时间（如 2 周），最后在支付服务 v3 移除旧字段。这就是向后兼容+逐步废弃的模式。

**Q5**：不应该回滚——P99 延迟劣化是可观测信号但从 200ms 到 500ms（仍在可接受范围），没有错误率和业务指标异常，说明系统仍然正确处理请求只是慢了。但也不应该继续放量。正确做法：(1) 暂停 Canary 自动放量（保持 1%），(2) 分析 Tracing 看延迟劣化发生在哪个 span（如数据库查询从 5ms 变成 200ms？新增的 API 调用到外部服务慢了？），(3) 判断根因——如果是新代码的已知 tradeoff（如新增了安全校验层）→评估是否可接受→可接受则继续放量；(4) 如果是未知问题（如 N+1 查询）→标记 BLOCKING→回滚修复后再部署。观察时间：每步至少 5 分钟（覆盖 Metrics 的聚合窗口），且必须覆盖至少一个完整的业务波动周期（如 15 分钟）。

**Q6**：排查范围的数量级差异。每周 2 次部署（每次 10-20 PR）：如果上线后发现 bug→需要在 10-20 个 PR 中找哪一个引入的问题→每个 PR 可能改了多个文件→总计可能涉及几十个文件和上百处变更→复杂度 = O(所有 PR 的变更并集)。每天 40 次部署（每次 1-3 PR）：发现 bug→排查范围只局限在最近一次部署的 1-3 个 PR→通常几分钟内就能定位到具体 PR 和 commit→复杂度 = O(1-3 个 PR 的变更)。这就像二分查找——每次部署越小，出问题时"二分"到的范围越精确。高频小批量部署的原则：减少每次部署的风险半径（Blast Radius），最终使部署变成低风险的"例行操作"而非"重大事件"。

（5/6 通过）
