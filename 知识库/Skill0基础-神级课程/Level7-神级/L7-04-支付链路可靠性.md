# L7-04：支付链路可靠性 —— 每笔订单都像银行转账一样分毫不差

> 🎯 **学支付系统的可靠性设计**：不是简单的"调用支付 API"，而是从幂等性、对账、回调验证、超时处理、退款补偿到财务级一致性的全链路保障。
> ⏱️ **预计时间**：45 分钟

***

> [!tip] 💡 白话小课堂
> 支付系统和其他系统的本质区别：少收一分钱是财务损失，多收一分钱是用户投诉+监管风险。支付的核心不是"调用支付API"，而是处理各种异常情况——回调丢了怎么办？回调重复了怎么办？回调金额和订单金额不一致怎么办？用户付了钱但订单显示未支付怎么办？这些问题比"正常支付"重要100倍。

> [!warning] ⚠️ 避坑指南
> 三大经典坑：1）只依赖被动回调——微信/支付宝的回调可能延迟甚至丢失，必须加主动查询兜底（每30s轮询支付状态）；2）回调签名用API Key而不是API v3证书——微信v3用的是独立证书私钥，用错会导致所有签名验证失败；3）金额单位搞错——微信金额是"分"，不转换直接存成"元"=100元的订单收1元。

> [!info] 🔑 核心秘诀
> 支付系统的六字真言：幂等、对账、双路径。幂等——同一个支付请求不管发多少次只扣一次钱（idempotency_key + 唯一约束）；对账——T+1日和支付网关逐笔比对，这是最后一道防线；双路径——被动等待回调+主动轮询查询，两条路都走才能不丢任何一笔支付。

## 1. 支付系统的独特挑战

```markdown
## 支付不同于其他业务——错一分钱都是事故

### 为什么支付特别难？

1. 涉及真实金钱
   → 多扣 1 分钱 → 用户投诉 → 监管介入
   → 少扣 1 分钱 → 财务损失 → 对账不平

2. 跨系统异步调用链
   → 你的系统 → 支付网关 → 银行 → 用户
   → 任何一环超时/失败都需要正确处理
   → 没有"大概成功了"——要么扣款要么不扣

3. 回调不可信
   → 第三方回调可能被伪造（签名验证）
   → 回调可能重复发送（幂等性）
   → 回调可能延迟到达（超时处理）

4. 资金安全
   → 退款必须精确到分
   → 重复退款 = 双倍损失
   → 支付状态不一致 = 财务灾难
```

## 2. 支付链路的核心设计模式

```markdown
## 六大核心模式

### 模式 1：幂等性（Idempotency）
  每次支付请求带唯一 idempotency_key：
    → 客户端生成 UUID → 服务端存储 key + 结果
    → 重复请求返回相同结果（不重复扣款）
    → 幂等键有效期：24 小时
  
  数据库实现：
    → UNIQUE(idempotency_key)
    → INSERT ... ON CONFLICT DO NOTHING RETURNING result

### 模式 2：两阶段支付（Two-Phase Payment）
  Phase 1: 创建支付意图（PaymentIntent）→ 状态 PENDING
  Phase 2: 确认支付（Confirm）→ 状态 PROCESSING → SUCCESS/FAILED
  
  好处：
    → Phase 1 和 Phase 2 之间可以插入风控检查
    → Phase 2 失败可以重试（PaymentIntent 不变）

### 模式 3：回调验证（Webhook Verification）
  收到支付回调必须验证：
    → 签名验证（HMAC-SHA256，用支付网关的公钥）
    → IP 白名单（只接受支付网关的 IP）
    → 金额校验（回调金额 == 订单金额）
    → 币种校验（CNY/USD 不能错）

### 模式 4：主动查询 + 被动回调（Poll + Webhook）
  不依赖单一路径：
    → 被动：等待支付网关回调
    → 主动：每 30s 查询一次支付状态（前 5 分钟）
    → 兜底：15 分钟后仍未确认 → 主动查询 + 人工介入

### 模式 5：对账（Reconciliation）
  每日对账流程：
    → 下载支付网关的对账单（通常 T+1）
    → 逐笔比对：我方订单 vs 网关流水
    → 差异分类：长款（网关扣了但我方未记录）、短款（我方记录了但网关未扣）
    → 自动修复 + 差异报告

### 模式 6：退款安全（Refund Safety）
  退款前必须验证：
    → 原支付订单存在且状态为 SUCCESS
    → 退款金额 <= 原支付金额
    → 退款总额（含历史部分退款）<= 原支付金额
    → 幂等键（防止重复退款）
```

## 3. 状态机设计

```markdown
## 支付状态机

  CREATED → PENDING → PROCESSING → SUCCESS
                    ↘            → FAILED
                    ↘            → CANCELLED (超时)
  
  SUCCESS → REFUNDING → REFUNDED (全额退款)
                     → PARTIAL_REFUNDED (部分退款)

## 订单状态与支付状态的关联

  | 订单状态 | 支付状态 | 允许的操作 |
  |---------|---------|-----------|
  | PENDING_PAYMENT | CREATED | 发起支付 |
  | PENDING_PAYMENT | PENDING | 取消订单 |
  | PENDING_PAYMENT | PROCESSING | 等待（不可取消） |
  | PAID | SUCCESS | 申请退款 |
  | CANCELLED | CANCELLED | 无 |
  | REFUNDED | REFUNDED | 无 |

## 关键约束
  → 状态只能向前流转（不可逆）
  → PROCESSING 是"不确定"状态——需要主动查询确认
  → 任何状态变更都需要记录事件（审计追踪）
```

## 4. 电商案例：支付链路"不漏一分钱"的可靠性设计

> 🛒 **实战案例**：某电商平台月GMV 1.2亿，日均支付订单6.5万笔，接入微信支付和支付宝双通道。历史痛点触目惊心：(1) 某月对账发现"网关独有"差异17笔共¥38,420——用户在支付平台付了钱但订单系统无记录，原因是回调服务OOM重启15分钟内丢失了所有回调；(2) 更有一次微信回调被伪造攻击，攻击者修改请求body中amount=1分就成功支付了¥299的商品。CTO下令："支付链路必须做到财务级准确——少收一分钱是损失，多收一分钱是事故。"
>
> **用 gstack 架构体系重构支付可靠性**：
> 1. /plan-eng-review 评审支付架构 → 设计6层保障：幂等性（idempotency_key UNIQUE约束）→ 回调签名验证（微信API v3证书私钥，非对称加密）→ 双路径确认（被动回调 + 主动轮询每15s查一次PENDING订单）→ 金额校验（回调金额与订单金额逐笔比对）→ 状态机约束（CREATED→PENDING→PROCESSING→SUCCESS/FAILED，不可逆）→ T+1自动对账（逐笔比对支付网关对账单）
> 2. /review 审查支付模块代码 → 发现CRITICAL Bug：回调签名验证错误使用了API Key做HMAC而非API v3证书私钥验证——导致所有合法回调被拒绝但错误被静默吞掉；金额单位未做"分↔元"转换——测试环境一直用¥0.01所以没暴露
> 3. /investigate 排查历史"已付未到账"投诉 → Iron Law（Iron Law：根因分析铁律）根因：支付服务每分钟GC暂停1.2s→回调处理超时→回调丢失→主动查询Worker每30s覆盖不够→修复：回调先写Kafka（削峰+持久化）+ 主动查询间隔降至15s + PENDING超5分钟自动升级人工工单
> 4. /qa exhaustive 支付全链路测试 → 构建2000笔模拟支付（随机丢弃30%回调、随机重复15%回调、随机篡改5%金额）→ 验证最终一致性：2000笔全部正确结算，0差异
>
> **效果**：
> - 支付对账差异率从0.27%降至0.001%（日差异从日均17笔降至<1笔）
> - "用户付了钱但订单未更新"客服投诉从周均43次降至0次
> - 支付伪造攻击防护：回调签名验证准确率100%（API v3证书验证），0伪造回调通过
> - 大促峰值QPS 12000时支付成功率99.97%，P99延迟320ms
> - 自动对账修复率：95%的差异由系统自动修复（补录订单/取消订单），仅5%需人工介入
>
> > 🔑 **启示**：支付系统的可靠性不来自单一机制，而来自纵深防御——幂等性防重复扣款、签名验证防伪造回调、双路径防回调节点故障、金额校验防篡改、状态机防非法流转、对账兜底所有失效。六层中任何一层单独失效都不会导致资金损失。核心工程原则：永远不信任单一数据来源——支付金额永远从服务端数据库读取（不从前端body取），回调签名永远用网关证书验证（不用API Key），支付状态永远双路径确认（不单靠被动回调）。

## 5. 动手实践

1. **为你的订单系统设计幂等性方案**：选择一个支付接口，设计 idempotency_key 的生成规则（如 `order_{orderId}_{timestamp}`），写一段伪代码处理"重复请求返回相同结果"的逻辑。
2. **画出支付状态机**：画出订单支付状态的完整状态转换图（待支付→支付中→已支付/已失败/已退款），标注每个状态转换的触发条件和超时处理。
3. **设计每日对账流程**：模拟 3 笔"问题订单"——1 笔我方有记录、支付平台无记录；1 笔支付平台有记录、我方无记录；1 笔金额不一致。为每种情况设计处理策略和人工介入条件。

> [!tip] 提示：支付系统的可靠性 = 幂等性 + 状态机 + 对账。三者缺一不可。幂等性防重复，状态机管流程，对账做最终兜底。

## 6. 掌握检验

**Q1**：支付系统的幂等性实现中，为什么"唯一约束 idempotency_key + INSERT ... ON CONFLICT DO NOTHING RETURNING result"比"IF EXISTS 检查然后 INSERT"更可靠？
- A) 没有区别，只是写法不同
- B) 后者存在竞态条件：两个并发请求同时 IF EXISTS（都返回不存在）→ 都执行 INSERT → 第二次可能成功并重复扣款。唯一约束 + ON CONFLICT 将检查和插入合并为数据库层的原子操作，彻底消除竞态窗口
- C) IF EXISTS 更快，适合高并发场景
- D) ON CONFLICT 只能在 PostgreSQL 使用

**Q2**：支付系统的"双路径"（被动回调 + 主动查询）设计分别防范什么风险？假设微信回调服务在你应用重启的 15 分钟内全部丢失——请描述双路径如何保证这 287 笔支付不丢失，并说明哪一条路径是最终兜底。

**Q3**：在支付状态机中，为什么 PROCESSING 状态被称为"不确定状态"？当一笔支付停留在 PROCESSING 状态超过 5 分钟时，系统应该如何判断和处理？
- A) PROCESSING 就是失败状态，直接取消订单
- B) 这是中间过渡状态，不需要特殊处理
- C) PROCESSING 意味着已向支付网关发起请求但未收到明确成功/失败——可能是网关处理中、网络超时、或回调丢失。应主动查询支付网关确认最终状态：查到 SUCCESS 则补录，查到 FAILED 则取消，查不到则继续等待或人工介入
- D) 自动重试发起支付，不管之前的结果

**Q4**：每日对账（T+1 Reconciliation）的四种差异类型分别是什么？为什么说"对账是最后一道防线"——如果前面所有防护（幂等性、回调验证、双路径）都失效了，对账如何兜底？

**Q5**：gstack /investigate 在支付回调丢失案例中运用了 Iron Law（确认根因后才修复）。请复述这个案例的根因分析四阶段（调查→模式分析→假设测试→修复），并解释：如果不遵循 Iron Law，只修了"主动查询"这个症状而没修"OOM 内存泄漏"这个根因，系统会面临什么持续风险？

**Q6**：在支付回调验证中，为什么必须用 API v3 证书（独立私钥）而不是 API Key 做签名验证？如果错误使用了 API Key，系统会暴露两个什么安全风险？

## 7. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** — IF EXISTS + INSERT 是两步操作，在高并发下有竞态条件：请求 A 和 B 同时执行 IF EXISTS 都得到 false，然后都执行 INSERT——如果 idempotency_key 有唯一约束，B 会报错（需要额外错误处理），如果没有唯一约束，B 会成功插入导致重复扣款。UNIQUE 约束 + ON CONFLICT 将"检查+插入"合并为数据库层的单一原子操作：要么插入成功返回新结果，要么冲突返回已有结果，无论多少并发请求都安全。这是"用数据库的 ACID 特性实现业务幂等"的标准模式。

**Q2**：被动回调负责正常路径（延迟低，实时性好），主动查询负责异常路径——防范回调节点故障、网络丢包、应用重启丢失回调。当应用重启 15 分钟内回调全部丢失：被动路径失效（15 分钟内无回调到达）。主动查询 Worker 每 30s 轮询过去 5 分钟内所有 PENDING 状态支付→查到微信返回 SUCCESS→补录订单状态为已支付。主动查询是最终兜底层——即使回调永久丢失，最迟 5 分钟后也会被主动查询发现并修复。双路径的核心思想：不依赖任何一个单一通道的可靠性。

**Q3**：**C** — PROCESSING 是"已发出扣款指令但结果未知"的状态：可能是支付网关正在处理、网络超时但扣款实际已成功、回调丢失。正确处理：等待 15 秒基础超时 → 主动查询支付网关状态 → 查到明确结果则更新状态 → 查不到则继续轮询（指数退避，最多 5 分钟）→ 5 分钟后仍无结果则标记为异常，提醒人工介入。不能直接取消（可能导致用户已扣款但订单被取消），也不能无限等待。

**Q4**：四种差异类型：(1) 一致：双方记录一致，正常；(2) 平台独有（长款）：我方有记录，网关无——可能是支付被风控拦截、回调丢失导致订单未取消；(3) 网关独有（短款）：网关有记录，我方无——可能是回调丢失导致未记录交易；(4) 金额差异：双方都有但金额不一致——可能是汇率波动、手续费差异、或金额篡改。对账作为最后一道防线：在前面所有实时防护（幂等性、签名验证、双路径）都失效的情况下，T+1 的对账会逐笔比对平台和网关的交易记录，发现任何差异→自动修复或人工介入。即使所有实时机制都失败了，最迟 T+1 日会发现并纠正。

**Q5**：四阶段根因分析：Phase 1 调查——客服反馈 287 笔支付未更新，日志显示 22:00-22:15 收到 0 条回调，微信后台显示 287 笔成功；Phase 2 模式分析——Nginx access log 显示 /payment/wechat/callback 返回 502，应用日志显示 OutOfMemoryError → 支付服务重启 15 分钟；Phase 3 假设测试——假设 OOM 是根因，验证：检查堆 dump → 确认大文件上传未关闭 InputStream → 复现 OOM；Phase 4 修复——修复 InputStream 泄漏 + 添加 Kafka 持久化回调 + 增加主动查询兜底。如果不修 OOM 根因只加主动查询：虽然主动查询能发现已丢失的支付，但应用仍可能在流量高峰期再次 OOM 重启，反复丢失数据，运维负担不断增加，且 OOM 可能从 15 分钟变成 30 分钟甚至更久。

**Q6**：API v3 证书是基于非对称加密的独立私钥签名机制——私钥只在你手中，支付网关用你的公钥验证签名。API Key 是对称密钥——你和网关共享同一个 Key，Key 泄露则攻击者可伪造一切。错误使用 API Key 的风险：(1) 回调伪造——攻击者获取 API Key 后可伪造任意支付成功回调（"我付了 0.01 元，但回调显示已付全款"）；(2) 签名验证全部失败——如果代码用 HMAC-SHA256(API Key) 校验但微信实际用证书私钥签名，所有合法回调都会被拒绝，而攻击者如果用 API Key 生成的签名反而可能通过验证。

（5/6 通过）
