# SKILL-OPTIMIZER

> 🤖 Skill 架构优化专家 — 诊断混乱、梳理流程、降低消耗、输出专业级方案。

---

## 零 Token 优先原则（⭐ 最高优先级）

**降本的第一性原理：能用本地工具执行的步骤，绝不用 AI。**

节省逻辑：
```
本地脚本/CLI → 0 token，几乎 0 成本，秒级响应
AI 模型调用 → 消耗 token，有成本，有延迟
```

在执行任何"AI 内优化"之前，必须先过一遍这个决策树：

```
这个步骤的本质是什么？
├── 调一个 HTTP API（飞书/Notion/GitHub/...）
│   → 查有没有 CLI：feishu CLI, gh CLI, notion CLI → 配置 CLI，脚本调用
├── 生成文件（PDF/图片/视频/音频）
│   → pandoc/chrome headless/ffmpeg/ImageMagick → 本地命令行
├── 搜索/过滤/格式化文本
│   → grep + jq + sed + python one-liner → 脚本
├── 网页截图/爬取
│   → headless browser CLI (playwright/chrome) → 本地脚本
├── 数据计算/转换
│   → python/node one-liner → 脚本
└── 真正需要推理/生成/分析/判断
    → AI 模型调用 → 进入 AI 内优化流程
```

### CLI/工具速查表

| 场景 | 替代方案 | 命令示例 | 节省 |
|------|---------|---------|------|
| 飞书文档/表格/知识库 | `lark-cli` (feishu CLI) | `lark doc +create` / `lark sheets` | **100%** |
| 即梦 AI 绘图 | 即梦 CLI（如有）或本地 Stable Diffusion | 本地推理 | **100%** |
| Markdown → PDF | pandoc / chrome headless | `pandoc in.md -o out.pdf` | **100%** |
| 网页截图 | chrome headless / playwright | `chrome --headless --screenshot` | **100%** |
| GitHub 操作 | `gh` CLI | `gh pr create` / `gh issue list` | **100%** |
| 图片处理 | ImageMagick / ffmpeg | `convert` / `ffmpeg` | **100%** |
| 视频处理 | ffmpeg | `ffmpeg -i in.mp4 ...` | **100%** |
| 文本搜索/统计 | grep / rg / jq | `rg "pattern" --json` | **100%** |
| 格式转换 | python -c / pandoc | `python -c "import json; ..."` | **100%** |
| Notion | notion CLI / api with curl | 脚本调用 Notion API | **100%** |

> 🔑 **判断口诀**：这个步骤如果让你用命令行做一次，你能做吗？能→就别让 AI 做。

## 可调参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `入口理解时限` | 30 秒 | 判定"入口清晰"的时间阈值 |
| `缓存有效期` | 5 分钟 | 重复调用拦截窗口 |
| `冗余合并阈值` | 80% | 两个状态相似度超过此值→合并 |
| `混乱升级阈值` | 40 | 混乱度超过此值→等级自动升一级 |
| `快速模式触发词` | "快速看"/"quick"/"一句话" | 用户消息含这些词→仅输出诊断总览 |
| `Prompt 冗余警戒线` | 30% | 冗余率超此值→标记需融合 |
| `降本红色阈值` | Token≥15000 或 API≥8次 或 延迟≥30s | 达标→🔴高消耗 |

## 三、诊断流程

> ⚠️ 快速模式下跳过 Step 2-4，直接出诊断总览。

### Step 1：读取解析

读入源文件，标记：工作流步骤、分支、状态、外部依赖、输入参数面、Prompt 块。

### Step 1.5：上下文收集（Phase 1 补全）

> 📚 L6-09 Phase 1：确认产品是什么、面向谁、项目类型

```
在深入诊断前，先向用户收集 3 个关键信息：

① 运行环境：Claude Code / Codex / 自定义 Agent / 其他？
② 调用频率：高频（每天≥10次）/ 中频 / 低频（偶尔用一次）
③ 用户水平：新手（需要更多解释）/ 熟练（可以跳步骤）/ 专家（只要结论）

收集方式：
  - 如果用户一次给了完整上下文 → 直接使用
  - 如果用户没给 → 在方案卡开头增加一段"假设：运行环境=Claude Code, 频率=中频, 水平=熟练"
  - 高频 Skill → 降本优先（每次节省 = 累积收益）
  - 低频 Skill → 可维护性优先（省 token 不如省理解成本）
```

### Step 1.6：竞品扫描（Phase 2 补全）

> 📚 L6-09 Phase 2：Layer 1 经典 / Layer 2 流行 / Layer 3 第一性

```
三层知识快速扫描（3 分钟内完成，不阻塞主流程）：

Layer 1（经典）：这个 Skill 所属类型的标准架构是什么？
  → 工具型标准：单 Prompt + 参数注入 + 模板输出
  → 流程型标准：显式状态机 + 错误恢复 + 幂等设计
  → 系统型标准：Agent 分解 + 记忆分层 + 降级策略

Layer 2（流行）：当前同类 Skill 有哪些常见优化手法？
  → 参考 CLI/工具速查表，检查此 Skill 类型常用的 Offload 手段

Layer 3（第一性）：这个 Skill 有什么特殊约束是标准架构没覆盖的？
  → 问：有什么是这个 Skill 必须做的、但同类 Skill 不需要做的？
  → 这个"必须做但别人不做"的事 → 就是优化不能碰的边界

扫描结果并入诊断总览表，以一句"Layer 3 关键约束"形式呈现。
```

### Step 2：复杂度打分（1-10 × 权重）

| 维度 | 标准 | 权重 |
|------|------|------|
| 步骤数 | 1-3=2分, 4-7=5分, 8-15=8分, 15+=10分 | ×2.0 |
| 分支深度 | 无=1分, 2-3路=4分, 4-7路=7分, 8+路/嵌套=10分 | ×1.5 |
| 状态依赖 | 无=1分, 单步缓存=4分, 跨步=7分, 持久记忆=10分 | ×2.0 |
| 外部调用 | 纯文本=1分, 1个API=3分, 2-4个=6分, 5+/含浏览器=10分 | ×1.5 |
| 并发可能 | 全串行=10分, 部分可并行=5分, 已并行=1分 | ×1.0 |

> 总分 = 步骤×2 + 分支×1.5 + 状态×2 + 外部×1.5 + 并发×1

### Step 2.5：AI 依赖性分析 ⭐

**对 Skill 的每个步骤分类：**

```
逐步骤标记：
  🤖 MUST-AI    — 必须 AI 推理/生成/判断（如：理解用户意图、生成创意方案）
  🔧 CAN-SCRIPT — 本质是数据操作，可用脚本替代（如：调 API、格式化输出、文件转换）
  📦 HAS-CLI    — 已有成熟 CLI/工具可直接调用（如：飞书操作→lark-cli、GitHub→gh）
```

**AI 依赖度 = CAN-SCRIPT 步骤数 / 总步骤数 × 100%**

| AI 依赖度 | 评级 | 动作 |
|-----------|------|------|
| ≤ 20% | 🟢 健康 | AI 只做决策，执行全走脚本 |
| 21-50% | 🟡 可优化 | 检查 CAN-SCRIPT 步骤是否有 CLI 可替代 |
| 51-80% | 🔴 高依赖 | **必须重构**——大量步骤在浪费 token 做脚本就能做的事 |
| > 80% | ⛔ 严重 | 这个 Skill 本质是个脚本套了 AI 壳，考虑整个改为代码 |

> 此项诊断**优先于所有其他优化**。AI 依赖度 > 50% → 优化方案的第一条必须是"将 CAN-SCRIPT 步骤替换为本地工具/CLI"。

### Step 3：混乱度诊断（1-10 × 权重）

| 症状 | 检测方法 | 权重 |
|------|---------|------|
| 命名混乱 | 同一概念多个名字 | ×1.5 |
| 流程断裂 | 步骤间隐式假设，无显式状态传递 | ×2.0 |
| 冗余重复 | 同一逻辑 ≥2 次 | ×2.0 |
| 死代码 | 定义了从未使用 | ×1.0 |
| 职责过载 | 一个步骤 ≥3 件不相关的事 | ×1.5 |
| 硬编码 | 魔术数字、写死的 URL/路径 | ×1.0 |

> 混乱总分 = 命名×1.5 + 流程×2 + 冗余×2 + 死代码×1 + 职责×1.5 + 硬编码×1
> ≤20 清晰 / 21-40 局部混乱 / 41-60 严重混乱 / 61+ 需重写

### Step 4：降本分析

```
Token 估算：系统Prompt ___ + 每轮用户___×___轮 + 工具输出___×___轮 = ___ tokens
API 调用：核心模型___次 + 子Agent___次 + 外部API___次 + 工具___次 = ___ 次
延迟：最长串行路径___步 × 每步___秒 = ___ 秒（可并行___步）

评级：🟢低消耗(Token<5K,API<3次,延迟<10s) / 🟡可优化 / 🔴高消耗(≥15K/≥8次/≥30s)

参考单价：Claude Sonnet $3/15M | DeepSeek ¥1/4M | GPT-4o $5/15M (per M tokens)
```

## 五、分级优化策略

> ⚠️ **Offload First** — 第一步永远是：过零Token决策树 + 查CLI速查表（见文件头部）。AI 内优化是做完 Offload 之后的事。

---

### 🔧 工具型（≤ 30）

**Offload**：→ 执行零Token决策树。CAN-SCRIPT ≥ 2 步 → 整个改写为本地脚本 + 最小 AI 决策点。

**架构优化**：
1. **指令融合** — 多个分散指令 → 一个分层指令块
2. **参数压缩** — 必填 ≤ 3 个，其余给默认值
3. **模板参数化** — `{{placeholder}}` 模板
4. **few-shot 精简** — 保留 1-2 个最简示例

**🤖 AI内优化**：删礼貌冗余词 / 分隔符替自然语言 / 示例代码最简版删注释

### ⚙️ 流程型（31-60）

**Offload**：→ 执行零Token决策树。每个步骤先查 CLI 速查表 → 配置 → 脚本化；子步骤（格式化/转换/检索）下沉到脚本层，AI 只传参数收结果。

**架构优化**：
1. **状态合并** — 两状态相似度 > `冗余合并阈值`(80%) → 合并
2. **并行化** — 无依赖步骤并发（脚本步骤天然并行）
3. **Early Exit** — 满足条件直接返回，不跑全程
4. **工具链压缩** — 嵌套 > 2 层 → 压到 2 层或直调
5. **幂等设计** — 同输入多次执行结果一致

**🤖 AI内优化**：缓存拦截 / 延迟加载 / 批量合并

### 🏗️ 系统型（61-90）

**Offload**：→ 执行零Token决策树。每个子 Agent 明确 AI/脚本职责分界；Agent 链管线化——脚本预处理→AI决策→脚本执行→AI审查→脚本输出，AI 只出现在决策+审查节点。

**架构优化**：
1. **Agent 职责重划** — 每 Agent 只做一件事；合并模糊、拆分过重
2. **缓存分层** — L1 会话级 → L2 项目级 → L3 全局级
3. **渐进式加载** — 关键路径优先，非关键延迟确认
6. **记忆衰减调参** — 调整衰减速率（默认 5%/周 → 按需调整）

**🤖 AI内优化**：
- 模型分层路由：简单判断→小模型，复杂推理→大模型
- 预热缓存：高频查询预计算 → 项目级缓存
- 上下文压缩：只传结论摘要，不传完整对话历史
- 退火策略：连续 3 次同类请求 → 自动切批量模式
- 配额感知：内置 token 预算，接近上限自动降级

## 六、架构梳理（混乱度 > 40 自动触发）

```
Phase A 解构：拆成独立功能块 → 标记类型（核心/辅助/格式化/死代码）
            → 画实际执行流（不是设计意图，是代码实际路径）

Phase B 归一：统一命名 → 提取重复 → 删除死代码 → 合并过度拆分

Phase C 重组：按"入口层 → 处理层 → 出口层"重新排布
            入口 = 解析+校验+默认值
            处理 = 核心逻辑+分支+外部调用
            出口 = 格式化+错误包装+输出

Phase D 验证：用 3 个真实输入走重组流程 → 输出等价确认
```

## 八、执行优化

> ⚠️ **执行铁律**：先协商、原子操作、逐条验证、失败回滚、全程留痕。

### 8.0 方案确认与协商

**在执行任何改动之前，必须完成此步骤，不可跳过。**

```
Step 0.1 — 呈现最终方案
  向用户展示完整的方案卡（第七节格式），方案卡末尾标注：
  "请逐条确认，可直接回复'全部执行'，或指定修改某条（如'第3条不要'/'第5条改成...'/'再加一条...'）"

Step 0.2 — 接收用户反馈
  用户可能：
  ├── "全部执行" → 进入 8.1 执行顺序
  ├── "第X条不要" → 删除该条，重新编号，再次确认
  ├── "第X条改成XXX" → 修改方案，再次确认该条
  ├── "再加一条XXX" → 评估新增条目的可行性，加入方案，再次确认
  └── "先只做 Round 1" → 拆分执行范围，只执行指定 Round

Step 0.3 — 合并用户建议
  用户建议与原有方案冲突时：
  ├── 用户建议明显更优 → 采纳，标注"按用户建议调整"
  ├── 用户建议有风险 → 指出风险，给出修正版，等确认
  └── 用户建议不可行 → 解释原因，给出替代方案

Step 0.4 — 锁定方案
  所有条目确认完毕 → 输出"方案已锁定，共 N 条，开始执行"
  锁定后不再修改方案内容，如需调整 → 重新走 Step 0.1-0.4
```

> **原则**：用户是这个 Skill 的使用者，最了解实际场景。优化方案 = 诊断框架 + 用户判断。框架是死的，判断是活的。

### 8.1 执行顺序协议

严格按照降本优先级排序执行，**不可跳级**：

```
Round 1 — Offload First（节省最大，优先执行）
  ├── [并行] 1.1a 替换 CAN-SCRIPT 步骤为本地脚本 ─┐
  ├── [并行] 1.1b 配置 lark-cli（如涉及飞书）   ├─ 无依赖，同时执行
  ├── [并行] 1.1c 配置 pandoc/chrome（如涉及PDF）┘
  └── [串行] 1.2 验证所有 CLI/脚本可用（依赖 1.1a/b/c 全部完成）
  └── [串行] 1.3 验证每个替换后输出等价（依赖 1.2）

Round 2 — 架构优化（结构调整）
  ├── [并行] 2.1a 状态合并 ─┐
  ├── [并行] 2.1b 并行化     ├─ 不同步骤互相独立
  ├── [并行] 2.1c Early Exit ┘
  └── [串行] 2.2 Agent 职责重划 / 管线化（依赖上面完成）
  └── [串行] 2.3 缓存分层 / 渐进式加载（依赖 2.2）

Round 3 — AI 内优化（锦上添花）
  ├── [并行] 3.1 Prompt 压缩 + 指令融合 + 模板参数化（同一 Prompt 块可批量改）
  ├── [并行] 3.2 模型路由 + 上下文压缩 + 配额感知（同一配置层可批量改）
  └── [串行] 3.3 few-shot 精简 + 输出裁剪（依赖 3.1 完成，避免改乱的 Prompt 上再裁）
```

> 每个 Round 完成后 → 暂停 → 输出该 Round 的改动摘要 → 用户确认 → 下一 Round

### 8.2 原子执行协议

**每条优化手法独立执行，遵守以下 5 步协议**：

```
Step A — 备份 & Diff
  创建备份：原文件名.bak
  记录改动前的关键指标（Token 估算、步骤数、API 调用数）

Step B — 应用改动
  只改一个手法，不改其他任何内容
  改动必须可独立回滚（改动范围 ≤ 1 个逻辑单元）

Step C — 三级验证（见 8.3）
  ① 等价性验证：同输入 → 同输出？
  ② 边界验证：极端输入 → 不崩溃？
  ③ 回归验证：其他步骤 → 无副作用？

Step D — 判定
  ✅ 三级全过 → 提交改动，记录 diff，进入下一条
  ❌ 任一级失败 → 立即回滚（见 8.4），标记该手法为"不适用"，进入下一条
  ⚠️ 等价性不满足但输出更优 → 暂停，向用户说明差异，等确认后提交

Step E — 留痕
  记录：{手法} | {改动位置} | {验证结果} | {Token 变化} | {回滚原因（如失败）}
```

### 8.3 三级验证协议

#### ① 等价性验证

```
取优化前的 Skill，用 3 个真实输入执行，记录输出。
取优化后的 Skill，用同样的 3 个输入执行。

通过条件：
  - 结构化输出（JSON/YAML/表格）→ 字段和值完全一致
  - 自然语言输出 → 核心结论和信息点一致（措辞可不同）
  - 文件操作 → 生成的文件内容等价

不通过处理：
  - 按 8.4 回滚
  - 在最终报告中标注"等价性差异"及原因
```

#### ② 边界验证

```
构造 3 类极端输入：
  空输入：用户什么都没给 → Skill 应该优雅退出或提示，不崩溃
  超长输入：用户给了 10 倍于正常的长度的输入 → 不超时、不截断核心逻辑
  错误输入：用户给了格式错误的内容 → 有明确的错误提示，不静默失败

通过条件：3 类全部不崩溃、不静默、有合理反馈
```

#### ③ 回归验证

```
检查改动是否影响其他步骤：
  - 改动涉及的状态变量 → 检查所有引用该变量的步骤
  - 改动涉及的函数/工具调用 → 检查所有调用方
  - 改动涉及的输出格式 → 检查所有消费该输出的下游

通过条件：所有受影响步骤行为不变
```

---

### 8.4 回滚协议

```
触发条件：
  - 三级验证任一级失败
  - 用户在看到中间结果后要求回退某条改动

回滚步骤：
  1. 从 .bak 文件恢复被改动的部分
  2. 重新执行等价性验证（确保回滚成功）
  3. 在日志中记录回滚原因
  4. 该手法标记为 ⛔不适用，跳过，进入下一条

注意：
  - 回滚只回滚当前这条手法，不影响已成功提交的之前手法
  - 如果回滚后连续 2 条手法失败 → 暂停，重新评估方案是否合理
```

### 8.5 执行后审计

全部手法执行完毕后，进行最终审计：

```
审计清单：
□ 重新执行完整诊断（复杂度 + 混乱度 + AI依赖度 + 降本分析）
□ 输出"优化前后对比方案卡"
□ 逐条确认 6 条专业级标准是否全部 ✅
□ 计算实际节省：Token 减少___% | API 调用减少___% | 延迟减少___%
□ 列出来实际执行的 CLI 工具及配置状态
□ 标注哪些手法因验证失败被回滚（及原因）

审计通过条件：6 条标准全部 ✅ 且 核心问题已解决
未通过 → 回到 Round 2 重新评估
```
