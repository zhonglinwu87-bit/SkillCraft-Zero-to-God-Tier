# L2-04：营销创意轰炸机 —— SKILL.md 与 references/ 的内容拆分设计

> 🎯 **学什么**：当 Skill 覆盖几十个场景、几百条数据时，如何用 `references/` 目录保持正文简洁——正文放「框架和方法论」，references 放「大规模数据和详细列表」。核心洞察：一个好的 Skill 正文应该让人 5 分钟读完就知道怎么用，如果超过 300 行，说明你把「说明书」和「百科全书」混在一起了。
> 💡 **难易度**：⭐ | ⏱️ **预计时间**：35 分钟

***

## 1. 课程概览

> 💡 **白话小课堂**：这个 Skill 就像一个创意点子贩卖机——它肚子里有 139 个经过验证的 SaaS（SaaS：软件即服务，按月/年订阅付费） 营销增长创意，按 15 个类别（SEO（SEO：搜索引擎优化）、社交媒体、邮件、活动、公关……）、预算（免费/低价/中价/高价）、时间线（快/中/慢）组织好。你只需要说「我要做 SEO 增长，给一些免费或低成本的创意」，它就吐出最合适的那批并告诉你每一步怎么做。但本课要学的不是这 139 个创意本身——而是**「当 Skill 内容量过大时，如何把正文和详细数据分开管理」这个设计模式**。

> **本课的独特定位**——大规模内容管理的拆分设计：

| 做法 | 全部塞进 SKILL.md | 正文+references拆分（本课） |
|------|-----------------|-------------------------|
| SKILL.md 长度 | 1000+ 行 | **~175 行** |
| AI 首次读取 | 消耗大量 token 读完全文 | 先读速查表，按需深入 |
| 新增一个创意 | 在 1000 行中找位置插入 | 在 references 里追加一行 |
| 用户阅读体验 | 翻不到头 | 5 分钟了解框架 |

> 🔑 **核心秘诀**：SKILL.md 就像餐厅的菜单——你看到菜品名称和一句话简介就能决定点什么。references/ 就像后厨的食谱——详细步骤、精确配料都在那里，但吃饭的人不需要看。正文放「怎么做」（框架、方法论、速查表），references 放「具体数据/详细列表」（139 条创意的完整细节）。

> ⚠️ **避坑指南**：很多 Skill 作者会把一切内容塞进 SKILL.md——结果正文 1000+ 行，AI 每次调用都要消耗大量 token（token：词元，AI 文本处理单位，直接影响费用） 通读全文，响应变慢且成本飙升。更糟的是，用户在正文中迷路——就像一本没有目录的 500 页百科全书。

## 2. 为什么 SKILL.md 不能无限膨胀？

### 2.1 Token 成本视角

```
SKILL.md = 1000 行（全部创意都塞进去了）
  → 每次 AI 使用这个 Skill → 读取 1000 行 → ~8000 tokens
  → 用户一个月用 100 次 → 800,000 tokens 仅用于读取 Skill 正文
  → 其中 80% 的创意用户根本没用到（他只要 SEO 类的，却读了邮件类的）
  → 大量 token 浪费在「永远不会被用到的内容」上

SKILL.md = 175 行（正文框架） + references/（详细数据）
  → AI 首次读取：175 行 → ~1400 tokens
  → 识别用户"要 SEO 创意" → 打开 references/ideas-by-category.md → 只读 SEO 章节
  → 100 次使用 → ~140,000 tokens（正文） + ~50,000 tokens（按需深读）
  → 节省约 80% token 消耗
```

### 2.2 AI 检索效率视角

```
没有速查表的检索过程：
  用户：「给我一些 SEO 增长创意」
  AI：读取 SKILL.md（1000 行）→ 逐行扫描 → 找到「SEO」关键词
     → 但这 1000 行里有 15 个类别，SEO 只是其中一个
     → 扫描时间 = O(n)，n 越大越慢
     → 而且容易漏——「SEO」可能出现在别的类别的交叉引用中

有速查表的检索过程：
  用户：「给我一些 SEO 增长创意」
  AI：读取 SKILL.md 中的分类速查表（15 行）→ 定位「SEO 类」→ 跳转到 references/ 对应章节
     → 检索时间 = O(1)（通过索引直达）
```

### 2.3 可维护性视角

```
全部在 SKILL.md：
  新增第 140 个创意 → 在 1000 行中找到正确的类别位置 → 插入
  → 改一个创意 → 在 1000 行中搜索 → 找到 → 修改
  → 维护成本随内容量线性增长

正文+references 拆分：
  新增第 140 个创意 → 打开 references/ 对应章节 → 追加一行
  → 改一个创意 → 在 references/ 对应类别中直接找到 → 修改
  → 维护成本恒定（每个类别独立管理）
```

> 🔑 **核心洞察**：拆分不是「偷懒」——是「让 Skill 在内容量增长时保持可用性」。一个只有 50 个创意的 Skill，塞进正文没问题。一个有 500 个创意的 Skill，不拆分就等于自杀。

## 3. 拆分判断标准 —— 什么放正文，什么放 references？

### 3.1 三句话判断法

```
问自己三个问题：

Q1: 这个内容没有它，AI 还能正确理解 Skill 的「核心方法论」吗？
  → 不能 → 放 SKILL.md（这是框架）
  → 能 → 继续问 Q2

Q2: 这个内容是「大规模列表/数据」吗？（超过 20 条同类条目）
  → 是 → 放 references/（这是数据）
  → 否 → 继续问 Q3

Q3: 这个内容 AI 每次使用 Skill 都需要读吗？
  → 是 → 放 SKILL.md（高频需要）
  → 否 → 放 references/（按需读取）
```

### 3.2 具体例子：marketing-ideas Skill 的拆分

```
放 SKILL.md（正文 ~175 行）：
  ✅ 核心方法论：「根据目标、预算、时间线三要素筛选创意」
  ✅ 分类速查表（15 个类别 × 1 行 = 15 行索引）：
     | 类别 | 典型策略 | 适用阶段 |
     | SEO | 程序化页面、工具型内容 | 早期-增长期 |
     | Social | UGC 活动、思想领导力 | 全阶段 |
     | ... | ... | ... |
  ✅ 5 个典型创意示例（每类 1 个，展示格式）
  ✅ 使用方式：用户怎么提需求、怎么筛选

放 references/（详细数据）：
  ✅ 139 个创意的完整列表（每个含步骤、预期成果、适用条件）
  ✅ 按 15 个类别分文件或分章节
  ✅ 每个创意的详细实施指南
```

### 3.3 拆分后的正反馈循环

```
正文短 → AI 快速理解框架 → 根据速查表定位 → 深读 references 相关章节
  → 下次使用 → 正文框架还在上下文里 → 直接跳到相关 references 章节
  → 用户换了类别（从 SEO 换到 Email）→ AI 只需深读 Email 章节
  → 正文框架持续有效，不需要重读
```

> 🔑 **设计要点**：拆分后的效果是——正文框架像是一个「常驻内存」的导航系统，references 像是「按需加载」的数据模块。这和 L1-14 的「内容支柱」设计异曲同工——不是每次都用全部内容，而是按需取用。

## 4. 创意筛选与匹配系统

### 4.1 三要素筛选框架

Skill 不是简单地把 139 个创意丢给用户——而是根据三要素精准匹配：

```
三要素：
  1. 目标（Goal）：SEO 流量？社交传播？邮件转化？合作伙伴？
  2. 预算（Budget）：免费 / $（低成本） / $$（中等） / $$$（高投入）
  3. 时间线（Timeline）：快速见效（1-2周） / 中期（1-3月） / 长期（3月+）

匹配逻辑：
  用户说：「我想要免费或低成本的 SEO 增长方法，最好能快速见效」
  → 筛选器：Goal=SEO, Budget=免费/$, Timeline=快速
  → 从 139 个创意中筛选出匹配的 8-12 个
  → 按「投入产出比」排序，优先推荐低投入高回报的
```

### 4.2 为什么筛选比全量更重要？

```
全量推荐（「这是全部 139 个创意，你自己看吧」）：
  → 用户一看 139 个 → 选择瘫痪 → 一个都不做
  → 这叫「把决策负担转嫁给用户」

精准推荐（「根据你的情况，这 8 个创意最适合你」）：
  → 用户一眼看到 8 个 → 每个都看看 → 挑 2-3 个执行
  → 这叫「帮用户做决策」
```

> 🔑 **设计要点**：筛选系统的核心价值不是「减少数量」，而是「减少用户的决策成本」。这和 L1-10 的「降低用户行动门槛」是同一设计原则——用户不是不想做营销，是需要有人帮他从「139 个选哪个」降到「3 个先做哪个」。

## 5. 结构拆解：大规模内容管理型 Skill 模板

从 L2-04 提取「大规模内容管理型」Skill 的通用模板：

```markdown
## 大规模内容管理型 Skill 模板

### 核心特征
→ 内容量大（100+ 条目、几十个场景）
→ 正文放框架和方法论，references/ 放详细数据
→ 核心价值 = 让 Skill 在内容量增长时保持可用性

### 通用结构

## SKILL.md（正文，目标 < 300 行）
├── 核心方法论（3-5 段话，讲清楚「怎么用」）
├── 分类速查表（索引——AI 用它导航到 references）
├── 典型示例（每类 1-2 个示例，展示格式）
├── 筛选/匹配逻辑（用户怎么描述需求）
└── 使用方式（输入 → 筛选 → 输出 的完整流程）

## references/（详细数据，可以无限长）
├── 按类别组织的详细内容
├── 每个条目的完整说明（步骤、示例、适用条件）
└── 可独立读取——AI 不需要读完所有 references 才能工作

## 拆分判断标准
Q1: 没有它，AI 能理解核心方法论吗？ → 不能 = 正文
Q2: 它是大规模列表/数据吗？（>20 条） → 是 = references
Q3: 每次使用都需要吗？ → 是 = 正文，否 = references
```

**什么时候用大规模内容管理型？** → 当 Skill 的内容量超过约 300 行时：知识库（50+ 概念）、创意库（100+ 点子）、案例库（30+ 案例）、模板库（20+ 模板）——任何「框架 + 大量数据」的场景。

## 6. 电商案例：直播间促销话术批量生成

> 🛒 **实战案例**：某家纺品牌在抖音做直播带货（主推乳胶枕，客单价 ¥169），主播每天播 6 小时需要持续不断地说话——压单、逼单、转款、互动、感谢。运营团队每周给主播准备话术，但人脑一天最多憋出 20-30 条，重复率高、新鲜感差。主播反馈「老粉都说我车轱辘话来回讲」。场均观看 8,200，场均 GMV ¥3,800，转化率仅 1.1%。
>
> **用营销创意轰炸机 Skill 生成 100 条直播钩子话术**：
>
> | 筛选条件 | 值 | 为什么 |
> |---------|-----|--------|
> | 目标 | 直播促销 + 逼单转化 | 直播场景的核心需求 |
> | 预算 | 免费/低成本策略为主 | 话术创意零成本，拼的是脑洞 |
> | 时间线 | 即时可用 | 本周就要播 |
>
> **匹配结果（从 139 个创意模板中筛出适配直播的 5 类，批量生成 100 条）**：
>
> | 话术类型 | 生成数量 | 典型话术示例 | 使用场景 |
> |---------|:--:|------|--------|
> | 压单话术 | 25 条 | 「这批次泰国原液进口只有 300 个，上次直播 11 分钟就空了——今天我不确定能不能撑过 15 分钟」 | 库存告急时逼单 |
> | 场景代入 | 20 条 | 「你想想每天早上脖子僵硬地醒来，和脖子轻松地醒来——差的不是睡眠时长，是一个枕头」 | 讲解卖点时制造痛点 |
> | 价格锚定 | 18 条 | 「商场同款乳胶枕 ¥599，我们工厂直发去掉品牌溢价去掉商场租金——¥169，而且不满意拆了睡过也退」 | 报价时锚定对比 |
> | 信任背书 | 17 条 | 「我们做了 300 个人的睡眠测试，87% 的人换了这个枕头后 3 天内入睡时间缩短了 11 分钟以上」 | 打消质量疑虑 |
> | 互动引导 | 20 条 | 「正在看的新粉打个『新人』，我让助理给你们发一个只有新粉能领的福利链接」 | 拉新转化 |
>
> **效果**（周末换新话术后第一周数据）：
> - 场均观看：8,200 → 11,500（新话术互动率更高，平台推流增加）
> - 场均 GMV：¥3,800 → ¥7,600（转化率从 1.1% → 2.3%）
> - 主播话术疲劳度：大幅降低——100 条轮换用，同样的逼单逻辑有 5 种不同表达
> - 话术准备时间：每周 6 小时（运营手写 30 条）→ 1 小时（Skill 生成 100 条 + 人工筛选优化 25 条优质话术）
> - 老粉评论变化：从「又是这套」→「今天换新词了哈哈」
>
> > 🔑 **启示**：直播间最大的成本不是货，是主播的嘴。6 小时不停说话，再好的主播也会词穷。营销创意轰炸机相当于给主播配了一个「永不枯竭的话术弹药库」——运营每周花 1 小时筛出 25 条好话术，主播就可以在 6 小时内保持新鲜感。
>

## 7. 掌握检验

**Q1**：根据课程的拆分判断标准，以下哪项应该放在 `references/` 而不是 SKILL.md 正文中？
- A) 创意筛选方法论和核心流程
- B) 5 个典型 SEO 创意示例
- C) 100+ 个详细创意的完整列表和分步实施指南
- D) 按预算和时间线筛选创意的框架说明

**Q2**：课程用「菜单 vs 后厨食谱」比喻正文和 references 的关系。这个比喻中，「菜单」对应什么？
- A) references/ 中的详细步骤
- B) SKILL.md 中的速查表和框架
- C) 用户在浏览器中看到的最终页面
- D) 完整的 139 个创意列表

**Q3**：为什么分类索引表（如 Ideas by Category 速查表）必须放在正文中而不是 references/ 里？
- A) 为了让 SKILL.md 看起来更长
- B) 分类索引是纯数据，符合 references 的定位
- C) AI 需要这个速查表作为「导航」，否则每次都要读完全部 5000 行才能定位创意
- D) 索引表包含 API 密钥需要保护

**Q4**：以下哪一项不符合「放 SKILL.md」的标准？
- A) 核心方法论框架（3 段话讲清楚怎么筛选创意）
- B) 5 个典型创意示例及说明
- C) 按 15 个类别逐一展开的 139 条创意的完整细节
- D) 按预算（免费/$-$$$/$$$$）筛选的框架逻辑

**Q5**：课程的核心判断标准是「正文放『怎么做』，references 放『具体数据/详细列表』」。请用你自己的话解释：如果反过来——把 139 条创意全部塞进 SKILL.md——会发生哪两个问题？

**Q6**：小明用 Skill 给宠物用品店获取了 20 个创意，他应该按什么顺序执行？为什么 Skill 会建议「先做 SEO 文章，再做社交活动，最后做付费推广」？

## 8. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**C** — 50+ 个创意列表属于「具体数据/详细列表」，应放 references/。方法论、少量示例、核心流程放 SKILL.md。一句话判断：正文放「怎么做」，references 放「具体数据/详细列表」。

**Q2**：**B** — 菜单（SKILL.md）让你看到菜品名称和一句话简介就能决定点什么；后厨食谱（references/）是详细步骤和精确配料。食客不需要看食谱，厨师需要的时候才查。

**Q3**：**C** — 如果没有速查表，AI 每次处理「给一些 SEO 创意」这样的请求时，需要通读 5000+ 行的完整创意库才能定位相关知识。速查表就是导航地图——AI 先看地图找到目标区域，再进入 references 读取细节。

**Q4**：**C** — 按 15 个类别逐条展开 139 个创意属于「大规模数据列表」，应放 references/。其他选项：方法论（A）、少量示例（B）、筛选框架（D）都属于「怎么做」，适合放正文。

**Q5**：两个问题：(1) SKILL.md 过长（可能 1000+ 行），AI 每次使用都需要消耗大量 token 读取全文，响应变慢且成本飙升；(2) 用户/AI 难以快速定位——就像一本没有目录的 500 页百科全书，翻到需要的内容靠运气。课程建议正文 < 300 行。

**Q6**：按「低投入高回报 → 高投入」排序。SEO 文章免费且长期有效（写一次持续带来搜索流量），社交活动低成本且传播快（话题挑战可以病毒传播），付费推广成本最高、是一锤子买卖。营销不是有钱就砸，而是「用最少的钱撬动最大的回报」——先做不花钱还有长期收益的。

（5/6 通过）
