# L2-15：产品营销上下文记忆 —— 共享基础设施型 Skill 设计

> 🎯 **学什么**：marketing 体系中最特殊的 Skill——它被所有其他 40 个 marketing Skill 引用，像一个共享的记忆体。核心洞察：如果没有这个 Skill，你每次让 AI 写文案、做竞品分析、设计引流磁铁……都需要重新介绍一遍「我的产品是什么、卖给谁、有什么优点」。有了它，写一次，到处用——所有 Skill 在干活前先读这份「产品身份证」。
> 💡 **难易度**：⭐ | ⏱️ **预计时间**：35 分钟

***

## 1. 课程概览

> 💡 **白话小课堂**：你正在用 40 个 AI marketing Skill——写文案的、做竞品分析的、设计弹窗的、生成创意点子的……但每次切换 Skill，AI 都像失忆了一样问：「你的产品是什么？目标客户是谁？卖点是什么？」你像复读机一样回答了 40 遍。product-marketing-context 这个 Skill 就是一劳永逸的解决方案——你花 20 分钟填好一份「产品身份证」，之后所有 Skill 干活前自动先读这份文件。就像新员工入职第一天先看员工手册，之后就知道公司是干什么的了。

> **本课的独特定位**——共享基础设施型 Skill：

| 类型 | 做事 Skill | 基础设施 Skill（本课） |
|------|----------|---------------------|
| 类比 | 厨师（你点菜他炒菜） | **冰箱**（本身不做菜，但没有冰箱食材全坏） |
| 功能 | 直接产出（文案、PPT、图表） | **为其他 Skill 提供上下文** |
| 使用频率 | 有需求才用 | **每个其他 Skill 每次使用前都读** |
| 典型例子 | cold-email, form-cro, slide-deck | **product-marketing-context** |

> 🔑 **核心秘诀**：上下文管理不是什么高科技——它就是「把说过的话写下来，下次别让我再说一遍」。但这个简单的习惯，当你和 40 个 AI Skill 协作时，省下的不是几分钟，是成吨的精力。

> ⚠️ **避坑指南**：没有共享上下文的后果——你让 Skill A 写文案，它问「你的产品是什么」；你切到 Skill B 做竞品分析，它又问「你的产品是什么」；切到 Skill C 做引流方案，它又问一遍。你像复读机一样回答了 40 遍同样的信息。更糟的是——3 个 Skill 给你的建议可能是基于 3 个不同版本的产品描述（因为你每次说的不完全一样）。

## 2. 12 个信息模块详解

### 2.1 产品身份证的完整结构

`.agents/product-marketing-context.md` 文件包含 12 个信息模块：

```
模块 1: 产品概述（Product Overview）
  → 一句话总结 + 3-5 句话扩展描述
  → 「AI 驱动的写作助手，帮助内容创作者节省 80% 写作时间」

模块 2: 目标受众（Target Audience）
  → 核心用户画像：谁在用你的产品？
  → 「独立开发者、小型内容团队、跨境电商运营」

模块 3: 用户画像/B2B ICP（Ideal Customer Profile）
  → B2B：公司规模、行业、职位、预算
  → B2C：年龄、兴趣、消费习惯

模块 4: 痛点与问题（Pain Points）
  → 你的用户在没有你的产品之前，在忍受什么？
  → 「每天花 3 小时写产品描述，英文不够好导致转化率低」

模块 5: 竞争格局（Competitive Landscape）
  → 主要竞品、间接竞品、替代方案
  → 不写「我们比 XX 好」——客观描述

模块 6: 差异化（Differentiation）
  → 你的产品有什么是竞品没有的？
  → 「唯一支持中英文混写优化的 AI 写作工具」

模块 7: 异议处理（Objection Handling）
  → 用户最常见的顾虑和你的回应
  → 「太贵了？」→ 「月费 ¥99，省一个全职写手 ¥8,000/月」

模块 8: 切换动力/JTBD（Jobs to Be Done）
  → 用户的「推力」（对现状不满）+「拉力」（对新方案的向往）
  → +「锚定」（对改变的焦虑）+「习惯」（对旧方案的依赖）

模块 9: 客户语言（Customer Language）
  → 用户怎么说你的产品？直接引用真实用户的话
  → 「终于不用每天写到半夜了」「比我花 3000 块请的写手还好」

模块 10: 品牌语调（Brand Voice）
  → 3-5 个关键词描述品牌风格
  → 「专业但不冷、温暖但不煽情、简洁但不简陋」

模块 11: 证据点（Proof Points）
  → 能证明你的产品有效的任何东西
  → 「5000+ 付费用户」「4.8 星 App Store 评分」「月省 80% 写作时间」

模块 12: 目标（Goals）
  → 你想通过营销达成什么？
  → 「Q3 目标：月付费用户增长到 10,000」
```

### 2.2 为什么是 12 个模块而不是 5 个或 20 个？

```
5 个模块太少：
  → 只有产品概述、目标受众、差异化、定价、品牌语调
  → 缺了「客户语言」——Skill 不知道用户怎么描述自己的痛点
  → 缺了「异议处理」——Skill 写文案时不会主动化解顾虑
  → 缺了「证据点」——Skill 不会在合适的地方加入信任信号

12 个模块刚好：
  → 覆盖了其他 40 个 Skill 需要的所有维度
  → 文案 Skill 需要：产品概述 + 目标受众 + 品牌语调 + 客户语言
  → 竞品 Skill 需要：竞争格局 + 差异化 + 异议处理
  → 引流 Skill 需要：痛点 + 目标受众 + 证据点
  → 每个 Skill 各取所需，不读不需要的模块

20 个模块太多：
  → 信息冗余——维护成本高
  → 用户填起来觉得烦（20 分钟 → 45 分钟）
  → 部分模块其他 Skill 从来不用——浪费
```

## 3. 两种创建方式

### 3.1 方式 A：从代码库自动生成（适合有官网的产品）

```
Skill 扫描你的官网和文档：
  首页 → 提取产品概述、价值主张
  功能页 → 提取核心功能列表
  定价页 → 提取价格和套餐
  关于页 → 提取品牌故事和团队信息
  FAQ → 提取常见异议和回应

→ 自动生成 .agents/product-marketing-context.md 草稿
→ 用户审核并手动补充（客户语言、品牌语调、内部目标）
→ 最终确认，正式启用
```

### 3.2 方式 B：对话式从零填写（适合新项目或没有官网的产品）

```
Skill 逐个模块提问，用户口述回答：

AI: 「先说说你的产品是做什么的——用一句话概括？」
用户: [口述]
AI: 「很好。现在告诉我谁在用你的产品？或者你最想让谁用？」
用户: [口述]
...（12 轮对话后）
AI: 「全部填完了。这是你的产品身份证，要看一下吗？」

→ 像和顾问聊天一样完成，不用写文档
→ Skill 自动整理成规范格式
```

## 4. 共享上下文的四条原则

### 4.1 原则详解

```
原则 1: 写一次，到处用（Write Once, Use Everywhere）
  → 用户在 product-marketing-context 中填一次产品信息
  → 所有 40 个 marketing Skill 自动读取
  → 用户永远不需要重复描述产品

原则 2: 能查到的别问（Don't Ask What You Can Look Up）
  → 其他 Skill 需要产品信息时 → 先读 product-marketing-context
  → 只有在文件里找不到时才问用户
  → 避免「你是什么产品」这种用户已回答过的问题

原则 3: 新信息追加不覆盖（Append, Don't Overwrite）
  → 用户在使用其他 Skill 时提供了新信息（如「最近拿到了红点奖」）
  → 自动追加到 product-marketing-context 的证据点模块
  → 不覆盖已有信息——用户之前写的内容保留

原则 4: 改了自动生效（Changes Propagate Automatically）
  → 用户修改 product-marketing-context 后
  → 所有 Skill 下次使用时自动读取最新版本
  → 不用通知每个 Skill「我更新了产品信息」
```

### 4.2 反向更新 —— Skill 使用中自动丰富上下文

```
场景：
  用户用 cold-email Skill 写开发信
  AI 问：「你的产品有什么独特的卖点？」
  用户回答：「我们最近刚拿了红点设计奖，这在我们的行业是第一家」

自动更新：
  product-marketing-context.md → 证据点模块
  「2026 年 4 月：获得 Red Dot Design Award（行业首家）」

下次：
  用户用 social-content Skill 写社交媒体帖子
  AI 自动在文案中加入 Red Dot Award 的信息
  用户不需要再说一次
```

> 🔑 **设计要点**：上下文文件不是写完就「冻住」的——它在每次 Skill 使用中「生长」。用户在和不同 Skill 的对话中泄露的零星信息，被自动捕获并追加到正确的模块中。上下文越用越丰富。

## 5. 结构拆解：共享基础设施型 Skill 模板

```markdown
## 共享基础设施型 Skill 模板

### 核心特征
→ 本身不产出内容——为其他 Skill 提供共享上下文
→ 被所有其他 Skill 引用
→ 写一次，到处用
→ 在使用过程中自动生长（反向更新）

### 通用结构

## Shared Context File（共享上下文文件）
- 位置：约定路径（如 .agents/product-marketing-context.md）
- 信息模块（N 个维度，每个维度服务不同 Skill）
- 每个模块：定义 + 用途 + 格式示例

## Creation Methods（创建方式）
方式 A: 自动生成（扫描现有资料）
方式 B: 对话式填写（用户口述，Skill 整理）

## Four Principles（四条原则）
1. 写一次，到处用
2. 能查到的别问
3. 新信息追加不覆盖
4. 改了自动生效

## Reverse Update（反向更新）
- 其他 Skill 使用中收集的新信息 → 自动追加到对应模块
- 上下文文件持续生长
```

**什么时候用共享基础设施型？** → 当多个 Skill 需要共享同一套基础信息时：产品信息（所有 marketing Skill）、用户偏好（所有配置型 Skill）、品牌资产（所有创意型 Skill）——任何「多个 Skill 都要知道同一件事」的场景。

**共享基础设施型与 L1-09 跨 Skill 偏好共享的关系**：

| | L1-09 跨 Skill 偏好共享 | **L2-15 共享基础设施** |
|------|------|------|
| 共享内容 | 用户偏好（主题、输出格式） | **产品信息（12 个模块）** |
| 引用方式 | Skill A 读 Skill B 的 EXTEND.md | **所有 Skill 读同一个 context 文件** |
| 更新方式 | 用户手动更新 | **使用中自动反向更新** |

## 6. 电商案例：客户画像整合驱动精准推荐

> 🛒 **实战案例**：某母婴电商 App（月活 45 万，主营奶粉+纸尿裤+辅食）的运营团队用 6 个不同的营销 Skill 做推送——push（push：App 推送通知） 用「最后一次购买品类」数据，短信用「会员等级」数据、EDM（EDM：电子邮件营销） 用「浏览记录」数据。问题是：这些数据来自不同系统，3 个 Skill 对同一个用户的认知完全不同——push Skill 认为她是「奶粉用户」，短信 Skill 认为她是「白银会员」，EDM Skill 认为她「最近在看辅食」。结果：同一用户收到三条互相矛盾的消息——push 推奶粉满减、短信推纸尿裤积分兑换、EDM 推辅食 85 折，用户觉得「这 App 是不是精神分裂」。
>
> **用 product-marketing-context Skill 建立统一客户画像上下文**：
>
> | 信息模块 | 填写内容 | 哪些 Skill 使用 |
> |------|---------|---------------|
> | 用户画像 | 宝妈、28 岁、宝宝 8 个月、混合喂养（奶粉+辅食）、月消费 ¥600-¥800、偏好进口品牌 | 所有营销 Skill |
> | 购买历史 | 最近 90 天：3 罐 A2 奶粉（每罐 ¥358）、纸尿裤 L 码 4 包、米粉 2 盒 | push Skill、短信 Skill |
> | 浏览行为 | 近 7 天：浏览「婴儿面条」5 次、「磨牙饼干」3 次、将「婴儿肉松」加入购物车但未付款 | EDM Skill、推荐引擎 |
> | 生命阶段 | 宝宝 8 个月 → 正在进入「辅食多样化窗口期」 | 所有 Skill（触发品类扩展推荐） |
> | 价格敏感度 | 奶粉选 A2 ¥358（偏高端）、纸尿裤选花王 ¥129（偏中端）→ 对入口食品价格不敏感、对消耗品价格敏感 | 促销 Skill（决定推券面额） |
> | 沟通偏好 | push 点击率 12%、短信打开率 3%、EDM 打开率 18% → 优先 EDM + push 双通道 | 渠道选择 Skill |
>
> **统一上下文驱动后**：所有 6 个 Skill 读取同一份上下文 → 同一用户收到的不再是三条矛盾消息，而是一条协同推荐链：EDM 推「宝宝 8 个月辅食指南 PDF」（引流磁铁）→ 3 天后 push 推「肉松+面条+饼干组合装 ¥99」（精准推荐，直接命中购物车未付款项）→ 下单后短信「赠品兑换码已发至您的 App」（售后维护）。
>
> **效果**（统一上下文上线 60 天 vs 上线前 60 天）：
> - 用户人均收到消息条数不变（4.2 条/周），但消息内容从「互不相干」变成「一条故事线」
> - 消息点击率：push 12% → 22%、EDM 18% → 31%、短信 3% → 7%
> - 交叉品类购买率（买奶粉的用户也买了辅食）：从 17% → 34%
> - 购物车放弃召回率：从 6.8% → 15.2%
> - App 卸载率：从月均 8.3% → 4.9%
>
> > 🔑 **启示**：精准推荐最大的敌人不是「数据不够」，而是「数据散落在不同系统里，每个 Skill 看到的都是盲人摸象」。product-marketing-context 相当于在 6 个营销 Skill 之上建立了一个「共享记忆层」——每个 Skill 干活前先读一遍完整的用户画像，确保 push、短信、EDM 讲的是同一个故事而不是三段互不相关的自言自语。
## 7. 掌握检验

**Q1**：product-marketing-context 被称为什么类型的 Skill？
- A) 执行型 Skill——直接产出营销内容
- B) 基础设施型 Skill——为其他 Skill 提供共享上下文，本身不产出内容
- C) 分析型 Skill——分析产品数据
- D) 自动化型 Skill——自动执行营销任务

**Q2**：product-marketing-context 文件包含多少个信息模块？
- A) 5 个
- B) 8 个
- C) 12 个
- D) 20 个

**Q3**：「反向更新」指的是什么？
- A) 用户手动修改 context 文件
- B) 其他 Skill 在使用过程中收集到的新产品信息，自动追加到 context 文件的对应模块
- C) Skill 把旧信息替换为新信息
- D) 从竞品网站抓取信息更新 context

**Q4**：为什么所有 marketing Skill 需要先读 product-marketing-context 再干活？
- A) 为了满足 GDPR 合规要求
- B) 如果没有产品上下文，AI 每次都需要问用户「你的产品是什么」，用户变成复读机
- C) 为了节省 API 调用成本
- D) 为了验证用户身份

**Q5**：四条原则中「能查到的别问」是什么意思？如果没有这条原则，用户会遭遇什么？请举一个具体场景说明。

**Q6**：假设你要为「宠物用品电商」创建一个 product-marketing-context。请至少填写 6 个模块的关键信息，并说明这些信息会如何被「cold-email」「social-content」「competitor-alternatives」三个 Skill 分别使用。

## 8. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** — product-marketing-context 是基础设施型 Skill——它本身不产出内容（不写文案、不做 PPT、不生成弹窗），而是为其他 40 个 marketing Skill 提供产品信息。类比：冰箱本身不做菜，但所有厨师都依赖冰箱里的食材。

**Q2**：**C** — 12 个信息模块：产品概述、目标受众、用户画像、痛点、竞争格局、差异化、异议处理、切换动力、客户语言、品牌语调、证据点、目标。这个数量覆盖了其他 Skill 需要的所有维度，又没有冗余到让用户填表 45 分钟。

**Q3**：**B** — 反向更新是 product-marketing-context 的独特设计——用户在使用其他 Skill 时泄露的零星信息（如「我们刚拿到红点奖」，「用户说比花 3000 请的写手还好」），被自动捕获并追加到 context 文件的对应模块。context 不是写完就冻住的——它在使用中持续生长。

**Q4**：**B** — 如果没有共享上下文，用户每换一个 Skill 就要重新描述一次产品。40 个 Skill = 回答 40 遍同样的信息。更糟的是——用户每次可能说得不完全一样，导致不同 Skill 基于不同版本的产品描述给建议，营销内容互相矛盾。

**Q5**：「能查到的别问」意味着其他 Skill 需要产品信息时，先读 product-marketing-context 文件。只有文件中找不到时，才问用户。没有这条原则的场景：用户用「写文案」Skill → AI 问「你的产品是什么」；用户切到「做竞品分析」Skill → AI 又问「你的产品是什么」；用户切到「设计弹窗」Skill → AI 再问一遍。用户一天被问十几次同样的问题，体验极差——而且 AI 显得很蠢（像每次见面都问「你叫什么名字来着？」）。

**Q6**：示例：(1) 产品概述：「高端宠物用品电商——有机宠物食品、环保玩具、定制项圈」→ cold-email 用于开发信介绍；(2) 目标受众：「25-40 岁城市宠物主，月宠物消费 ¥500+」→ social-content 用于确定内容风格和话题；(3) 差异化：「所有食品可溯源到具体农场，每批有第三方检测报告」→ competitor-alternatives 用于对比页的核心论点；(4) 客户语言：「『我家猫只吃这家的粮了，别的碰都不碰』」→ social-content 用于 UGC 活动的素材方向；(5) 证据点：「TrustPilot 4.9 星，3,800+ 评价」→ cold-email 用于社交证明；(6) 异议处理：「比超市贵？」→ 「超市粮 ¥30/kg，我们 ¥80/kg——但超市粮的肉含量只有 4%，我们是 70% 真肉」。三个 Skill 各取所需：cold-email 用模块 1+6+5、social-content 用模块 2+4、competitor-alternatives 用模块 3+6。

（5/6 通过）

</details>
