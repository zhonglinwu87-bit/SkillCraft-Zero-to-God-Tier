# L2-10：批量目录提交 —— 批量化 Skill 的「定位变体 + 断点追踪」设计

> 🎯 **学什么**：如何设计一个「同一个操作重复 N 次但每次参数不同」的 Skill——定位变体策略 + CSV（CSV：逗号分隔值表格格式） 断点追踪。核心洞察：批量化不是说同一句话说 100 遍，而是同一个意思用 4 种角度各说 25 遍——在技术社区强调 API 有多快，在设计社区强调界面有多美，在创业社区强调增长有多猛。
> 💡 **难易度**：⭐ | ⏱️ **预计时间**：35 分钟

***

## 1. 课程概览

> 💡 **白话小课堂**：你的 SaaS（SaaS：软件即服务，按月/年订阅付费） 产品做好了但没人知道——你去 Google 搜「最好的 AI 写作工具」，出来的全是竞品。你需要让你的产品出现在各种目录网站上（Product Hunt、G2、AlternativeTo……），但手动一个个提交？100 个网站 = 至少一周的全职工作。这个 Skill 就像一个超级勤奋的秘书——你给它产品信息，它自动生成 4 种定位变体（技术版、设计版、创业版、通用版），然后按目录列表逐个提交，用 CSV 表追踪进度。即使中途电脑蓝屏，下次打开 CSV 就知道「第 47 个已完成，从第 48 个继续」。

> **本课的独特定位**——批量化 Skill 的「定位变体 + 断点追踪」模式：

| 做法 | 手工提交 | 批量化 Skill（本课） |
|------|---------|-------------------|
| 100 个目录 | 逐个打开、填写、提交 | **1 套产品信息 × 4 种定位变体 × 自动提交** |
| 中途中断 | 不记得做到哪了 | **CSV 追踪表 = 断点续传** |
| 不同目录 | 同一段产品描述复制粘贴 | **4 种定位变体适配不同受众** |
| 100 个站 | 一周全职 | **半天** |

> 🔑 **核心秘诀**：批量化不是说同一句话说 100 遍，而是同一个意思用 4 种角度各说 25 遍。同一个产品在技术社区强调 API，在设计社区强调 UI，在创业社区强调增长——同一碗面，配料不同才能适应不同人的口味。

> ⚠️ **避坑指南**：最常见的批量化事故——提交到第 47 个网站时电脑蓝屏了，你不记得哪些已经提交了哪些没提交，结果要么漏了 20 个，要么重复提交被当垃圾信息封号。追踪表就是你的断点续传。

## 2. 定位变体策略 —— 为什么不能说同一句话 100 遍？

### 2.1 同一个意思，四种角度

```
产品：AI 写作 SaaS 工具

技术社区版（HackerNews, Dev.to, ProductHunt 技术区）：
  「API-first AI 写作引擎——3 行代码接入内容生成，支持 GPT-4o 和 Claude。
   99.9% uptime, 平均响应 800ms。」
  → 强调技术指标、API 接入、性能数据

设计社区版（Dribbble, Behance, DesignerNews）：
  「不只内容，连排版美学都帮你考虑——AI 写作 + 自动排版，
   输出直接可用于 Notion、Medium、微信公众号。」
  → 强调设计感、输出美观、多平台适配

创业社区版（Product Hunt, BetaList, IndieHackers）：
  「从 0 到 5000 付费用户——我们用 AI 帮内容创作者省下 80% 写作时间。
  单人创始人，月经常性收入 $12K。」
  → 强调增长数据、创始故事、商业成果

通用/营销版（G2, Capterra, GetApp）：
  「AI 驱动的写作助手——输入主题，3 分钟出高质量文章。
   支持 30+ 语言，10,000+ 活跃用户。」
  → 强调功能、用户数、通用价值
```

### 2.2 定位变体的设计原则

```
原则 1：核心信息不变，呈现角度变化
  → 不是编造不同的产品定位——是同一个产品从不同视角看
  → 「生成速度快」在技术版 = 「平均响应 800ms」
                    在创业版 = 「用户说比竞品快 3 倍」
                    在设计版 = 「无需等待，实时预览」

原则 2：每个变体要像一个「真人写的」，不像「模板改的」
  → 批量提交最怕被识别为「模板化垃圾信息」
  → 4 种变体让 100 个提交看起来像 4 个不同的人写的
  → 不是一次写 4 个然后复制粘贴 25 次——是 4 种不同的叙事角度

原则 3：受众决定角度
  → 不是「我有 4 个版本，每个目录随机挑一个」
  → 而是「这个目录的读者是谁 → 用对应的版本」
```

## 3. CSV 追踪表 —— 批量化操作的断点续传

### 3.1 为什么必须有追踪表？

```
没有追踪表：
  第 1-30 个目录：顺利提交（以为都记住了）
  第 31 个目录：电脑崩溃 / 网络断了 / 被人叫去开会
  回来之后：我做到第几个了？第 30 还是第 31？
  → 打开第 30 个 → 「这个好像提交过了？」
  → 打开第 31 个 → 「这个是还没提交还是提交失败了？」
  → 焦虑、重复提交、遗漏提交

有追踪表：
  每次提交后 → 在 CSV 里记一笔 → Status 从 pending → submitted
  崩溃后 → 打开 CSV → 最后一条 submitted 是第 30 条
  → 从第 31 条继续
  → 1 秒定位，零焦虑
```

### 3.2 追踪表的标准字段

```csv
Directory,URL,Category,Positioning,Status,SubmittedDate,ResponseDate,Result,Notes
Product Hunt,https://producthunt.com/...,创业,创业版,submitted,2026-05-10,,,等待审核，预计 3-5 天
BetaList,https://betalist.com/...,创业,创业版,pending,,,,需要先注册账号
TAAFT,https://theresanaiforthat.com/...,AI目录,技术版,approved,2026-05-08,2026-05-12,已上线,排名第 24
G2,https://g2.com/...,通用,通用版,rejected,2026-05-09,2026-05-15,需要 5 条真实评价,先收集评价再重新提交
```

**各字段用途**：

| 字段 | 用途 | 为什么重要 |
|------|------|-----------|
| Directory | 目录名称 | 快速识别 |
| Status | pending/submitted/approved/rejected | 进度一目了然 |
| SubmittedDate | 提交日期 | 知道多久了该去跟进 |
| ResponseDate | 响应日期 | 知道审核周期 |
| Result | 最终结果 | 知道哪个成功了哪个失败了 |
| **Notes** | 自由备注 | **最重要的字段**——记录上下文 |

### 3.3 Notes 字段的实战价值

```
好的 Notes：「ProductHunt 已提交，准备配合 3 周预热，目标发布时间 5/25。
            需要提前联系 5 个 Hunter 确认支持。」

好的 Notes：「已拒，原因是需要提供试用账号。
            下次提交前先创建 demo 账号，账号信息存 LastPass。」

好的 Notes：「提交后 7 天无响应。已发 follow-up 邮件（5/20）。
            如果再过 7 天仍无响应，考虑放弃。」

差的 Notes：「已提交」
差的 Notes：「ok」
差的 Notes：（空着）

→ Notes 的价值 = 下次打开时不需要回忆或推理当时的上下文
→ 批量化可能跨越数天甚至数周——Notes 是「写给未来的自己的备忘录」
```

## 4. 七级目录体系 —— 不同目录不同策略

### 4.1 为什么分级？

```
70+ 个目录不能一视同仁：
  → Product Hunt 的流量是「冷门 AI 目录」的 1000 倍
  → G2 需要 5 条真实评价，不是「提交就完事」
  → BetaList 审核严格，描述需要精心打磨
  → 一些冷门目录可以快速批量提交

分级 = 按重要性分配精力：
  Tier 1（核心目录）→ 精心准备，每字必究（3-5 个）
  Tier 2（优质目录）→ 用定位变体，提交后跟进（10-15 个）
  Tier 3（长尾目录）→ 快速批量提交（50+ 个）
```

### 4.2 Product Hunt 深度攻略

Product Hunt 是所有目录中流量最大、竞争最激烈的——需要单独的策略：

```
发布前 3 周：
  □ 创建 Product Hunt 即将发布页面
  □ 准备产品截图、Logo、Tagline（40-60 字符）
  □ 联系 5-10 个 Hunter（有影响力的人）请求支持
  □ 准备 Maker Comment（产品故事、为什么做这个、未来计划）
  □ 准备社交媒体预热（Twitter/LinkedIn 预告发布日期）

发布日：
  □ 早上 12:01 AM PST 发布（Product Hunt 按天排名）
  □ 第一时间回复所有评论
  □ Maker Comment 要真诚、有人味儿——不是 PR 稿

发布后：
  □ 感谢所有支持和评论的人
  □ 发布回顾文章（「我们在 Product Hunt 上的经历」）
  □ 把 Product Hunt 的 badge 挂在官网上
```

## 5. 结构拆解：批量化 Skill 模板

从 L2-10 提取「批量化」Skill 的通用模板：

```markdown
## 批量化 Skill 模板

### 核心特征
→ 同一个操作重复 N 次，但每次参数（或角度）不同
→ 核心挑战 = 大规模 ≠ 模板化（避免被识别为垃圾信息）
→ 核心设计 = 定位变体 + 断点追踪

### 通用结构

## Batch Workflow（批量化流程）
1. 收集基础信息（产品名、描述、链接、Logo）
2. 生成定位变体（2-4 个角度）
3. 目标列表分级（Tier 1/2/3）
4. 逐个执行（每个完成后更新追踪表）
5. 最终检查（追踪表中所有 Status 非 pending）

## Positioning Variations（定位变体）
Variation A: [受众A的角度] — 关键词/侧重点
Variation B: [受众B的角度] — 关键词/侧重点
Variation C: [受众C的角度] — 关键词/侧重点

## Tracking System（追踪表）
必需字段：ID, Target, URL, Status, Date, Result, Notes
Status 流转：pending → submitted → approved/rejected
Notes = 写给未来的自己的备忘录

## Tier System（分级体系）
Tier 1: 核心目标（3-5 个）— 精心准备
Tier 2: 优质目标（10-15 个）— 跟进
Tier 3: 长尾目标（50+ 个）— 快速批量
```

**什么时候用批量化？** → 当同一个操作需要在 N 个不同的目标上执行时：目录提交（70+ 个目录）、社交媒体发布（多平台分发）、邮件群发（个性化批量发送）——任何「1 套核心信息 × N 个目标」的场景。

**批量化与 L2-04 大规模内容管理型的关系**：

| | L2-04 大规模内容管理型 | **L2-10 批量化** |
|------|------|------|
| 核心设计 | 正文 vs references 拆分 | **定位变体 + CSV 追踪** |
| 核心挑战 | 内容太多放不下 | **重复操作不能乱、不能漏** |
| 关键系统 | 速查表 | **追踪表（断点续传）** |

## 6. 电商案例：多平台商品目录批量同步上架

> 🛒 **实战案例**：某家居品牌卖家同时在淘宝、拼多多、抖音三个渠道开店，每次上新 30 款收纳产品，需要在三个平台分别手动填写商品类目、标题、属性、价格、图片——30 款 x 3 个平台 = 90 次重复填写。运营每次上架需要 2 天，而且经常出现「淘宝上架了 28 款，拼多多忘了上 2 款」的遗漏。
>
> **用批量化 Skill 做多平台同步上架**：
>
> | 步骤 | 操作 | 关键设计 |
> |------|------|---------|
> | 1. 产品信息表 | 30 款商品的标题、属性、价格、图片一次填好 | 一套信息，三平台复用 |
> | 2. 标题变体 | 淘宝版（30 字短标题+卖点前缀）拼多多版（60 字长标题+搜索词堆叠）抖音版（口语化短标题+话题标签） | 3 种平台标题策略 |
> | 3. 平台分级 | Tier 1（淘宝）：精调每个标题，确保搜索权重Tier 2（拼多多）：批量导入，重点检查价格敏感词Tier 3（抖音）：快速上架，标题口语化即可 | 按平台流量权重分配精力 |
> | 4. 同步提交 | Tier 3 抖音快速批量（30 分钟）Tier 1 淘宝精调（每款 3 分钟 x 30 款 = 1.5 小时） | 分级投入精力 |
> | 5. 追踪 | CSV 追踪表记录每款商品在每个平台的上架状态 | 断点续传，零遗漏 |
>
> **效果**：
> - 三平台同步上架 30 款商品总耗时从 2 天降至 2.5 小时（CSV 追踪零遗漏）
> - 平台间标题覆盖率不一致问题消除（之前常出现淘宝标题优化了但拼多多用的是旧版标题）
> - 拼多多搜索曝光上涨 210%（平台适配的长标题+搜索词堆叠策略）
> - 抖音商品卡点击率从 1.8% 升至 3.2%（口语化标题 + 话题标签）
>
> > 🔑 **启示**：多平台运营最大的浪费不是上架花时间，而是「不同平台上的信息不统一」——淘宝改了标题拼多多没改、拼多多降价了抖音还是旧价格。批量化 Skill 用一套产品信息表驱动三个平台同步上架，CSV 追踪表确保 30 款 x 3 平台 = 90 次操作零遗漏。

## 7. 掌握检验

**Q1**：批量化 Skill 为什么必须有追踪系统（如 CSV 追踪表）？
- A) 方便向老板汇报工作进度
- B) 防止中途中断后不知道哪些已提交、哪些未提交——避免漏提交或重复提交被封号
- C) 追踪系统能自动填写提交表单
- D) CSV 格式比数据库更快

**Q2**：课程中的定位变体策略，对于「宠物画像定制」产品，在创业/副业目录中应该强调什么？
- A) 画风有多美、插画师有多厉害
- B) 「从 0 到月销 300 单的宠物定制画像品牌，真人画师团队 15 人」
- C) 「你家狗子值得的不只是手机照片，挂在墙上才叫爱」
- D) 产品价格和优惠信息

**Q3**：以下关于批量化 Skill 的描述，哪一项是**错误**的？
- A) 批量化是说同一句话在不同平台说 100 遍
- B) 批量化是同一个意思用不同角度说——在技术社区强调 API，在设计社区强调 UI
- C) 定位变体让提交不显得是「模板化垃圾信息」
- D) 不同目录有不同受众，需要不同面向的产品描述

**Q4**：大威在提交宠物目录时用了「宠物社区版描述」，在提交设计目录时用了「设计版描述」。这体现了什么原则？
- A) 越多描述版本越好
- B) 同一碗面，配料不同才能适应不同人的口味——定位变体策略
- C) 所有描述版本需要完全不同的产品定位
- D) 应该只用一个描述版本保持一致性

**Q5**：大威的批量提交流程中，追踪 CSV 表记录了哪些字段？为什么「Notes」字段也很重要？举一个实际例子说明。

**Q6**：假设你有一个 AI 写作 SaaS 产品，需要提交到 3 种目录：技术社区（如 HackerNews）、创业社区（如 ProductHunt）、通用目录（如 Crunchbase）。请为这 3 类目录各写一句 1 句话的产品定位描述。
