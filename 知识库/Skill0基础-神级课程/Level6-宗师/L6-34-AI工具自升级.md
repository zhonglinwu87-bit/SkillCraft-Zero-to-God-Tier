# L6-34：AI工具自升级 —— 让你的开发工具像App一样自动更新

> 🎯 **学 gstack 的自我升级机制**：不是手动 git pull 和重新构建，而是自动检测新版本、运行迁移脚本、保持向后兼容——让工具自己维护自己，开发者专注于业务代码。
> ⏱️ **预计时间**：20 分钟

> 💡 **新手提示**：工具自升级就像手机 App 自动更新——你不需要手动下载安装包，系统自动检测、下载、安装。对开发者来说，这意味着你始终拥有最新的安全修复和功能，而不用操心版本管理。

***

> [!quote]- 📖 原Skill精要
> **技能名称**：gstack-upgrade
> **核心功能**：升级 gstack 到最新版本。检测全局安装 vs 项目内安装，运行升级流程，展示更新内容。自动检测版本更新并在所有 Skill 的 preamble 中提示用户。支持迁移脚本处理破坏性变更，确保向后兼容。
> **所属体系**：gstack 虚拟工程团队
> **协作关系**：被所有 gstack Skill 的 preamble 引用——每次运行任何 Skill 时自动检测升级

## §1 课程概览

gstack-upgrade 是 gstack 的自我升级系统。它解决了开发工具领域的一个根本问题：工具升级的门槛导致大量用户停留在旧版本（"能用就不动"的心理）。解决方案是"每次 skill 调用时自动检测新版本"——将升级从"用户主动操作"变成"系统自动提醒"。核心机制包括：preamble 触发检测（对比本地和远程 VERSION）、内联升级流程（fetch + reset + build）、迁移系统（幂等脚本处理破坏性变更）、checkpoint + 自动回退（升级失败不留下半损坏安装）。本课通过双11大促期间的工具升级决策案例，展示了 PATCH/MINOR/MAJOR 版本在封网期间的分级策略。

> [!tip] 白话小课堂
> 工具应该自己维护自己。**gstack 的自我升级就像手机 App 自动更新**——每次你用任何 skill 的时候它都会偷偷检查一下有没有新版本。关键设计是**迁移系统**：升级不只是 git pull，还要跑迁移脚本处理破坏性变更。每个迁移脚本必须是**幂等的**（跑 10 次和跑 1 次结果一样），升级失败自动回退到升级前的状态——就像游戏存档，死了能读档。**大促期间能不能升级？** PATCH（修 bug）可以升，MINOR（新功能）等等再说，MAJOR（大改）打死不动。这节课教你在"稳定压倒一切"和"安全修复必须上"之间做正确判断。

## §2 自我升级的设计哲学——工具应该自己维护自己

### 传统工具升级的痛点

传统工具升级：看到 GitHub release → 手动下载 → 解压 → 配置 → 测试 → 祈祷不破坏现有工作流。升级周期：数周到数月。结果：大量用户停留在旧版本（"能用就不动"的心理）。这不仅是便利问题——它是安全问题：不升级意味着不使用安全修复。在 gstack 的数据中，如果只在启动时检测一次升级，开发者可能全天 8 小时使用有已知安全漏洞的版本。

### gstack 的自我升级核心理念

- **每次 skill 调用检查是否有新版本**：不是"用户想起来才检查"，而是"每次用工具时自动检查"
- **发现新版本 → 自动或半自动升级**：用户可以配置 `auto_upgrade true` 实现完全自动（推荐保留手动确认）
- **运行迁移脚本处理不兼容变更**：从 N-5 版本升级到当前版本的完整路径被测试和保障
- **升级后立即可用**：无需手动配置——构建 + 迁移 + 验证一体化

### 升级检测时机——为什么是"每次 skill 调用"而非"启动时一次"？

传统方案"启动时检测一次"的根本盲区：开发者早上 9 点打开终端（gstack v1.7.0.0）→ 10 点安全修复 v1.7.1.0 发布 → 开发者全天使用 gstack 处理了 20 个 PR——所有操作都在有已知安全漏洞的旧版本上执行。如果有一个 PR 恰好触发这个漏洞，开发者可能无意中让漏洞进入代码库。

gstack 的方案：每次 skill 的 preamble 执行 `gstack-update-check` → 对比本地 VERSION 与 origin/main 的 VERSION → 如果有新版本 → 在 skill 输出中嵌入 `UPGRADE_AVAILABLE` → 四选项 AskUserQuestion。

成本分析：一次 `git fetch`（增量下载，通常 < 1KB）+ 一次文本对比（VERSION 文件 < 100 字节）+ 绝大多数情况下的"无更新"快速返回 = < 1s 延迟, < 10KB 网络开销。与"错过安全修复可能导致的后果"相比完全可以接受。

## §3 升级流程——从检测到完成的五步状态机

### Step 1: 检测（每次 skill 调用）

`gstack-update-check` 对比本地和远程版本。输出: `UPGRADE_AVAILABLE <old-version> <new-version>`。仅在 git 仓库模式下检测（非 vendored 安装不检测——因为无法 git fetch）。

### Step 2: 提示（首次发现时）

AskUserQuestion 四个选项：
- **A) 立即升级（推荐）**→ 继续 Step 3
- **B) 这次跳过，下次提醒** → 记录 snooze 状态，1 天后再次提示
- **C) 这次跳过，看到 changelog 再说** → 打开 CHANGELOG.md（让用户做出知情决策）
- **D) 不再提醒这个版本** → 记录永久跳过（但下个版本会重新提示——不能永久关闭安全更新）

### Step 3: 执行升级

```bash
cd ~/.claude/skills/gstack
git fetch origin
git reset --hard origin/main
bun run build  # 重新编译 browse + design + 生成 SKILL.md
```

### Step 4: 运行迁移

扫描 `gstack-upgrade/migrations/` 目录，运行所有版本号在当前和升级后之间的迁移脚本。迁移脚本处理：配置格式变更（JSON → YAML）、目录结构重组（`~/.gstack` → `~/.gstack/projects`）、数据文件迁移、清理过时文件。

### Step 5: 验证

运行 self-test（基本功能验证）。如果通过 → `JUST_UPGRADED <from> <to>`。如果失败 → 回退到之前的版本。

### 完整状态机

```
检测到新版本 → 提示用户 → 用户选择"立即升级"
→ 自动创建 checkpoint: git stash（保存当前状态）
→ 执行升级: git fetch && git reset --hard origin/main && bun run build
  ├── 成功 → 运行迁移脚本
  │   ├── 成功 → 运行 self-test
  │   │   ├── 通过 → 输出 JUST_UPGRADED → 完成
  │   │   └── 失败 → 回退: git stash pop → "升级验证失败，已回退"
  │   └── 部分失败 → 记录警告但不阻塞（迁移设计为"失败不阻塞升级"）→ 进入 self-test
  └── 失败（网络中断/git fetch 失败）→ 回退: git stash pop → "升级下载失败，已回退"
```

checkpoint 的价值：无论升级在哪个阶段失败，都能回到"升级前的确切状态"——不会留下半升级的损坏安装。

## §4 迁移系统——处理破坏性变更

### 为什么需要迁移？

软件升级经常涉及破坏性变更：配置文件格式改了（YAML → JSON）、数据存储路径变了（`~/.gstack` → `~/.gstack/projects`）、某些文件需要重新生成、旧版本残留文件需要清理。没有迁移系统的升级 = 升级后的工具找不到配置文件、读不到旧数据、"莫名其妙不 work"。

### 迁移脚本规范

每个迁移文件放在 `gstack-upgrade/migrations/`：
- **文件名**: `MIG-<version>-<description>.sh`
- **幂等性**: 可以安全地多次运行——这是硬性要求（详见下文）
- **错误处理**: 失败时不阻塞升级（记录警告——总比让升级卡死好）
- **回退**: 提供逆向迁移（如可能）

### 幂等性为什么是硬性要求？

非幂等迁移的问题场景：

迁移脚本将配置文件从 JSON 转为 YAML：
```bash
# 非幂等版本（有 bug 的设计）
cat config.json | yq -P > config.yaml && mv config.json config.json.bak
```

执行序列：①第一次运行 → 成功 → 生成 config.yaml，config.json 被重命名为 .bak。②升级失败 → 回退到旧版本 → 旧版本需要 config.json → 发现文件不在了 → 旧版本无法启动！③重新升级 → 迁移脚本再次运行 → `cat config.json` 失败（文件不存在）→ 迁移脚本报错 → 升级中断。

**幂等版本**（正确设计）：
```bash
# MIG-v1.5.0.0-migrate-config-to-yaml.sh
OLD_CONFIG=~/.gstack/config.json
NEW_CONFIG=~/.gstack/config.yaml
if [ -f "$OLD_CONFIG" ] && [ ! -f "$NEW_CONFIG" ]; then
  # 只在"旧格式存在且新格式不存在"时才执行迁移
  cat "$OLD_CONFIG" | yq -P > "$NEW_CONFIG"
  mv "$OLD_CONFIG" "${OLD_CONFIG}.bak"
  echo "✓ Migrated config from JSON to YAML"
fi
```

即使运行 10 次也不会有副作用——"旧格式存在且新格式不存在"的条件在第一次运行后就不再满足。

### 迁移的测试要求

- 每个迁移脚本必须通过测试
- 在 CI 中验证迁移脚本的正确性
- 确保升级路径（从 N-5 版本升级到当前版本）的完整性——不能假设用户只跳过 1 个版本

## §5 自动升级 vs 手动控制——安全措施与频率建议

### 自动升级配置

- `gstack-config set auto_upgrade true` → 每次自动升级（检测到新版本直接升级，不询问）
- `gstack-config set auto_upgrade false` → 手动确认（默认——推荐）

### 升级安全措施

- 升级前自动创建 checkpoint（git stash）
- 升级失败自动回退（git stash pop）
- **不升级处于 FREEZE 状态的仓库**（封网期间——工具也不能变）
- **不升级有未提交变更的仓库**（提示先提交——避免 stash 冲突）
- **团队模式**：只有团队成员可以触发升级（防止外部贡献者意外升级团队工具链）

### 升级频率建议

- **建议保留在最新版本**：享受最新修复和功能
- **连续 3 个版本不升级** → 强烈建议升级：可能错过了安全修复
- **生产关键期** → 可以延迟升级，但不建议跳过超过 3 个版本

## §7 电商 Skill 案例：双11封网期间gstack工具链升级决策

> 🛒 **实战案例**：双11前3天，电商平台已进入代码封网期（freeze状态）。gstack发布了v1.7.1.0 PATCH版本——修复了prompt injection检测的一个边界情况（安全分类器的正则未覆盖Unicode同形字符绕过）。运维负责人需要在"封网期间升级工具"和"不升级留下已知漏洞"之间做决策。

> - **升级检测与风险评估**：`gstack-update-check`自动检测——当前版本v1.7.0.0、可用版本v1.7.1.0(PATCH)、变更文件清单：`security-classifier.ts`（更新注入检测正则，+12行-4行）、`migrations/MIG-v1.7.1.0-clean-sessions.sh`（清理过期session文件）、无配置变更、无API变更、无skill行为变更。风险评估LOW——PATCH版本仅修复bug、向后兼容、迁移脚本仅清理无害文件。
> - **"封网期间是否升级"的决策框架**：反对升级的理由——封网期间所有变更都有风险（即使是工具链），升级失败可能让团队在双11前失去gstack的QA/审查/部署能力。支持升级的理由——安全修复在大促期间尤其重要（攻击者会利用大促高峰期发动攻击：流量越大攻击面越大），不修复意味着未来3天（封网期+双11当天）攻击者可能利用已知的prompt injection绕过安全分类器攻击客服AI。决策结果——**立即升级**。理由是安全漏洞被攻击的代价（客服AI被注入→泄露用户订单数据）远大于升级失败的风险（自动回退机制3分钟内恢复）。
> - **升级执行与验证**：执行流程——`cd ~/.claude/skills/gstack && git fetch && git reset --hard origin/main && bun run build`→构建成功、迁移脚本`MIG-v1.7.1.0-clean-sessions.sh`清理47个过期session文件→升级后验证：`/health`正常运行、`/qa`测试套件通过、`/ship` PR创建正常、最关键——对已拦截的prompt injection样本集重新跑安全分类器→之前漏掉的Unicode同形字符绕过现在被正确拦截。全程耗时4分钟。
> - **大促期间工具升级分级策略**：基于此次决策提炼出三级策略——PATCH（仅修复bug）允许升级（风险低、收益明确、安全修复大促期间更需要）；MINOR（新功能）延迟到大促后（新功能即使向后兼容也可能引入未知行为，行为变化本身就是风险）；MAJOR（破坏性变更）绝不在大促期间升级（迁移脚本可能出错、回退可能不完整）。关键原则：封网只针对业务代码，不冻结工具链的安全修复。

> 🔑 **启示**：自升级系统的价值不在于"自动升级"的自动化——而在于升级决策的"数据化"。变更分析（具体哪个文件变了、多少行、什么类型）+ 风险评估（PATCH/MINOR/MAJOR分级）+ 回退保障（自动stash + git reset --hard可逆）让升级决策从"凭感觉"变为"凭变更分析"。"封网期不升级任何东西"是一个好直觉，但安全修复是对这个直觉的合理例外——数据支撑下的例外比盲目的规则更可靠。

> [!info] 参考来源
> 工具自我升级模式参考了 [Homebrew](https://github.com/Homebrew/brew) 的 auto-update 机制和 [Rustup](https://github.com/rust-lang/rustup) 的工具链管理理念。迁移系统参考了 Rails migration 的版本管理模式。
## §8 掌握检验

**Q1**：gstack 的自我升级检测在什么时机触发？
- A) 系统启动时检测一次
- B) 每次 skill 调用时通过 preamble 执行 gstack-update-check，对比本地和远程 VERSION
- C) 开发者手动运行 `gstack check-update` 时检测
- D) 每周定时任务自动检测

**Q2**：大促封网期间（FREEZE），gstack 自升级的推荐策略是什么？
- A) 所有版本都不升级——工具也不能变
- B) PATCH 版本（仅修复）可以升级（风险低、收益明确），MINOR（新功能）延迟到大促后，MAJOR（破坏性变更）绝不在大促期间升级
- C) 所有版本都应该立即升级以确保安全
- D) 只在 git push 时升级

**Q3**：迁移脚本的"幂等性"为什么是硬性要求？请给出一个非幂等迁移脚本导致问题的具体场景——假设迁移脚本 `MIG-v1.5.0.0-migrate-config.sh` 在第一次运行时成功迁移了配置文件，但由于某种原因（升级失败后回退再重新升级）被第二次运行，非幂等的脚本会产生什么后果？

**Q4**：gstack 升级流程中，升级前自动创建 checkpoint（git stash）和升级失败自动回退的机制如何配合工作？请描述从"检测到新版本"到"升级成功"（或"升级失败 + 回退"）的完整状态机——包括每一步的成功/失败分支。

**Q5**：为什么 gstack 设计为"每次 skill 调用时检测升级"而非"启动时检测一次"？请从以下两个角度分析：①如果一个开发者连续使用了 8 小时的 gstack 没有重启终端，启动时检测会导致什么信息滞后？②每次 skill 调用检测的成本（网络请求 + 版本对比）是否值得？

**Q6**：大促期间 PATCH 版本的安全修复（如 prompt injection 检测的边界情况修复）被批准升级。但假设这个 PATCH 的"修复"改变了安全分类器的行为——导致之前不被拦截的一些边界输入现在被拦截了（增强了安全性但改变了行为）。请问：这算是 PATCH 还是 MINOR？行为改变（即使是安全增强）在封网期间的风险如何评估？如果这个 PATCH 导致了一个合法用户请求被误拦截（False Positive），在大促期间这可能造成多少 GMV 损失？

## §9 答案

**Q1**：**B** —— 升级检测在每次 skill 调用时通过 preamble 自动执行。核心理由：安全修复可能在任何时间发布——如果只在启动时检测，开发者可能全天使用有漏洞的版本。

**Q2**：**B** —— PATCH（仅修复）→ 允许升级（风险低，收益明确——安全修复更重要）；MINOR（新功能）→ 延迟到大促后（新功能可能引入未知行为，即使向后兼容，行为变化本身就是风险）；MAJOR（破坏性变更）→ 绝不在大促期间升级。

**Q3**：非幂等迁移的场景：迁移脚本 `cat config.json | yq -P > config.yaml && mv config.json config.json.bak`。第一次运行：成功，config.json 被重命名。升级失败 → 回退到旧版本 → 旧版本需要 config.json → 发现文件不在了 → 旧版本无法启动。重新升级 → 迁移脚本再次运行 → `cat config.json` 失败 → 迁移脚本报错 → 升级中断。幂等版本：`if [ -f config.json ] && [ ! -f config.yaml ]; then cat config.json | yq -P > config.yaml; fi`——即使运行 10 次也不会有副作用。

**Q4**：状态机详见 §3。关键路径：检测 → 提示 → 创建 checkpoint（git stash）→ 执行升级 → 运行迁移 → self-test。任何阶段失败 → git stash pop → 回到升级前状态。checkpoint 确保不会留下半升级的损坏安装。

**Q5**：①信息滞后：早上 9 点启动终端（v1.7.0.0）→ 10 点发布 v1.7.1.0 → 全天 20 个 PR 都在有漏洞版本上处理。②成本分析：git fetch（增量 < 1KB）+ 文本对比（VERSION < 100 字节）+ 绝大多数情况"无更新"快速返回 < 1s。与"错过安全修复"的后果相比完全值得。而且 git fetch 结果被缓存，同 session 内后续检测零成本。

**Q6**：仍应算 PATCH——变更本质是"修复了一个安全检测的边界情况"（之前漏掉了应被拦截的输入），不是"添加新功能"。风险评估：误拦截合法用户 → 高峰期 1% 误拦 = 5 个用户失去客服 → GMV 损失取决于客单价。但这个风险应与"不修复导致安全漏洞被利用"对比——攻击者造成的数据泄露远大于几个误拦截用户。最终判断是人工的——gstack 提供信息，人做决策。
