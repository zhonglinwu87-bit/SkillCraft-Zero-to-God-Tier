## 1. 课程概览

> 💡 **白话小课堂**：design-html 解决的是一道"最后一公里"难题——设计定了、方向批了，但把它变成可运行的网页代码，传统方式是"打开 Figma、手动量间距、手写 HTML/CSS、反复调"，这是体力活。design-html 把这个过程自动化：读入获选的设计方向、提取设计 token、选择正确的 Pretext 排版层级、生成语义化 HTML——而且文字是真的在正确排版的（不是 CSS 近似，是 Pretext 计算出的精确布局），最后启动实时预览让用户逐轮精细化，用 Edit（而非 Write）保留用户的手动文本编辑。

## 2. 为什么需要 Pretext？

```markdown
## The Text Layout Problem

传统 CSS 的文本布局受限于浏览器引擎的"黑盒"测量：
  → 你无法精确知道一段文字在特定宽度下会有多高
  → 你无法让卡片高度精确匹配内容（除非用 JS 手动计算）
  → 你无法在 Canvas/SVG 中做正确的文字排版
  → 聊天泡泡的宽度无法"紧贴"文字（CSS 只能全宽或内联）

Pretext（@chenglou/pretext）解决的就是这个问题：
  → prepare(text, font) → 一次性文本测量
  → layout(handle, width, lineHeight) → 次毫秒级的布局计算
  → 可以在 resize、contentEditable、动态内容变化时重复调用
  → 30KB 开销，零依赖

design-html 的使命：生成"文字真的在正确工作"的 HTML。
不是 CSS 近似——是计算出的布局。
```

## 4. Pretext 层级与 API 路由

不同的设计类型需要不同的 Pretext API。design-html 自动分析设计并选择正确的层级：

````markdown
## Pretext 层级选择

| 设计类型 | Pretext API | 关键能力 |
|---------|-------------|---------|
| 简单布局（landing, marketing） | prepare() + layout() | 缩放感知的高度计算 |
| 卡片/网格（dashboard, listing） | prepare() + layout() | 自定尺寸卡片 |
| 聊天/消息 UI | prepareWithSegments() + walkLineRanges() | 紧贴泡泡、最小宽度 |
| 内容密集（编辑、博客） | prepareWithSegments() + layoutNextLine() | 文本绕过障碍物 |
| 复杂编辑 | 全引擎 + layoutWithLines() | 逐行手动渲染 |

## 四个核心 Pretext 模式

### Pattern 1: 基础高度计算
```js
// 1. 准备（一次性，字体加载后）
const prepared = new Map()
for (const el of elements) {
  prepared.set(el, prepare(el.textContent, getComputedStyle(el).font))
}

// 2. 布局（廉价，每次 resize 调用）
function relayout() {
  for (const [el, handle] of prepared) {
    const { height } = layout(handle, el.clientWidth, lineHeight)
    el.style.height = `${height}px`
  }
}

// 3. 缩放感知
new ResizeObserver(() => relayout()).observe(document.body)

// 4. 可编辑内容
new MutationObserver(() => {
  prepared.set(el, prepare(el.textContent, font))
  relayout()
}).observe(el, { characterData: true, subtree: true })
```

### Pattern 2: 紧贴容器（聊天泡泡）
→ 二分搜索找到产生相同行数的最窄宽度
→ 泡泡不再"所有消息一样宽"——真的紧贴文字

### Pattern 3: 文本绕过障碍物
→ layoutNextLine 迭代器允许每行不同最大宽度
→ 文字真正流绕图片、引用块、侧边栏

### Pattern 4: 逐行渲染
→ layoutWithLines 返回 {lines: [{text, width, x, y}...], height}
→ 用于 Canvas/SVG 渲染或自定义 DOM 定位
````

## 5. 生成与优化循环

````markdown
## HTML 生成要求

始终包含：
  ✅ Pretext 源码（内联或 CDN）
  ✅ CSS 自定义属性（从 DESIGN.md 或 Step 1 提取）
  ✅ Google Fonts via <link> + document.fonts.ready 门控
  ✅ 语义 HTML5（<header>, <nav>, <main>, <section>, <footer>）
  ✅ 响应式 via Pretext relayout（不只是 media queries）
  ✅ 375px / 768px / 1024px / 1440px 断点
  ✅ ARIA 属性、标题层级、focus-visible 状态
  ✅ contenteditable + MutationObserver（编辑后重新计算）
  ✅ ResizeObserver（缩放后重新布局）
  ✅ prefers-color-scheme（暗色模式）
  ✅ prefers-reduced-motion（尊重动效偏好）
  ✅ 真实内容（绝不 lorem ipsum）

绝不包含（AI 懒人黑名单）：
  ❌ 默认紫色/蓝色渐变
  ❌ 通用三列功能网格
  ❌ 无视觉层级的居中布局
  ❌ 不来自模型图的装饰性 blob/波浪/几何图形
  ❌ 库存照片占位 div
  ❌ "Get Started" / "Learn More" 通用 CTA
  ❌ 带阴影的圆角卡片作为默认组件
  ❌ emoji 作为视觉元素
  ❌ 通用推荐区块
  ❌ cookie-cutter hero（左文右图）
````

> ⚠️ **避坑指南**： AI 生成 HTML 最常见的毛病是"lorem ipsum 占位"和"紫色渐变"。用真实内容填充——真实的产品名、真实的价格、真实的用户评价——你才能知道文字溢出在哪里、卡片会不会被长标题撑破。

## 6. 实时预览与精细化

```markdown
## 实时预览服务器
→ 生成 HTML 后启动 python3 -m http.server
→ 用户浏览器中实时预览
→ 每次 Edit 后刷新浏览器即可看到变化

## 验证截图
→ 如果 $B 可用：在 375px / 768px / 1440px 三个视口截图
→ 内联展示给用户（Read 工具）
→ 检查：文字溢出、布局崩溃、响应式断裂

## 精细化循环（最多 10 次迭代）
LOOP:
  1. 用户打开浏览器中的 HTML
  2. 如果有获选模型图 → 内联展示做视觉对比
  3. AskUserQuestion：有什么需要改的？说"done"结束
  4. 如果"done" → 退出循环
  5. 应用反馈（用 Edit 做手术式修改，不重写整个文件）
  6. 简短总结变更（2-3 行）
  7. 如果有验证截图 → 重新截图确认
  8. 回到 LOOP

为什么用 Edit 而非 Write？
→ 用户可能通过 contenteditable 手动编辑了文本
→ 重写整个文件会丢失这些手动修改
→ 手术式编辑保留了用户的改动
```

> 🔑 **核心秘诀**：精细化循环用 Edit 而不是 Write——这是关键设计决策。

## 9. 电商 Skill 案例：设计稿转代码——活动落地页

> 🛒 **实战案例**：618大促前，某电商平台设计师在Figma中完成了"精华液专场"活动落地页的设计稿（移动端375px为主，含Hero顶图+3款主推商品卡片+限时倒计时条+底部固定CTA按钮）。设计总监确认了设计方案，现需将设计稿转为前端代码（Vue.js + Tailwind CSS），且必须像素级还原。

> design-html从设计稿到可运行代码的完整流程：
> - **输入检测**：检测到`approved.json`存在（design-shotgun已确定"实验室解谜风"方向），自动读取DESIGN.md中的设计Token——展示字体DM Serif Display、数据字体IBM Plex Mono、主色#1A1A2E、强调色#00C9A7、背景#F7F7F2、间距基准8px、最大内容宽度960px。
> - **Figma解析**：通过Figma API读取设计稿节点结构，识别出7个关键区域——Hero区（渐变背景+主打标题+CTA按钮）、倒计时条（红色#EF4444+等宽字体数字）、3张商品卡片（产品图+名称+核心成分标签+价格+已售数量）、底部固定CTA（"立即抢购 ¥299"按钮）。自动识别了6个设计Token与Figma节点的映射关系。
> - **Pretext自适应排版**：商品标题和描述文本长度不一，使用Pretext引擎为每段文本预计算渲染高度——layout(handle, cardWidth=343px, lineHeight=1.5)→返回精确高度。确保3张商品卡片即使描述长度不同（48字/72字/35字），卡片整体高度仍然一致（340px），不会出现参差不齐。
> - **响应式断点**：375px移动端——单列纵向滚动，商品卡片全宽343px，Hero标题20px粗体；768px平板——双列商品卡片并排，Hero标题28px；1440px桌面——三列布局，最大内容宽度960px居中。三个断点的间距和内边距均基于8px基准缩放。
> - **代码质量检查**：生成的Vue.js组件自动通过了Pretext精确度验证（设计稿中标注的文本行数vs代码渲染行数偏差<2%）、颜色对比度验证（CTA按钮白色文字#FFFFFF在#1A1A2E背景上对比度12.6:1远超AA标准4.5:1）、无障碍检查（倒计时数字加了aria-label="距离结束还有2小时15分钟"）。

> **出码结果**：1个Vue.js组件文件（197行）+ 1个Tailwind配置文件补充（15行）。设计还原度检查——使用design-review的像素对比工具，Figma设计稿vs浏览器渲染截图的像素差异率为0.7%（行业可接受标准<2%）。移动端Lighthouse性能评分93/100（图片使用WebP格式+懒加载），首屏渲染时间1.2秒。

> 🔑 **启示**：设计稿转代码最难的不是"把视觉还原"——而是处理文本长度不一致导致的卡片高度参差、响应式断点下的信息优先级变化、以及设计稿中的固定像素值在4K屏上变成蚂蚁字的问题。好的design-html流程在这些问题发生之前就通过Pretext和Token系统把它们解决了。

```
生成后自动提取并在 DESIGN.md 中补充：
  → 圆角值：图片 0px（直角），卡片 4px，按钮 4px
  → 阴影：卡片 box-shadow: 0 1px 3px rgba(26,26,46,0.08)
  → 过渡：all 150ms ease-out
  → 新增动效：hover 时卡片微微上浮（transform: translateY(-2px)）
```

### 精细化循环迭代

```
迭代 1：创始人反馈——"成分表像药瓶标签，太冷了"
  → Edit：成分表添加暖灰背景底色 + 微圆角

## 11. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** —— Pretext 解决的核心问题是文本布局的精确计算。

**Q2**：**C** —— 这是 evolve 模式。

**Q3**：**C** —— 聊天界面需要 Pattern 2（紧贴容器）。

**Q4**：如果用户在浏览器中通过 contenteditable 手动编辑了产品描述文本（改了几句话、调整了措辞），但设计上只需要修改一个按钮的颜色——这时如果用 Write 重写整个 HTML 文件，用户手动编辑的内容会全部丢失。用 Edit 只改按钮的颜色样式，保留用户在其他区域的所有手动修改。这就是"手术式修改"——只动需要动的部分。

**Q5**：①长度差异——lorem ipsum 的段落长度是固定的（"Lorem ipsum dolor sit amet..."），而真实的产品描述可能是 50 字也可能是 200 字。用 lorem ipsum 测不出文字在极限长度下的卡片表现（短文字卡片空洞？长文字卡片撑破？）。②词长和换行点——lorem ipsum 的词长分布是拉丁语的（长词居多），而真实中文的词长完全不同。Pretext 的 layout() 计算分行点依赖于真实字符流——lorem ipsum 换出的行数和位置与真实内容不同，Pretext 计算的精确高度也会失准。最终结果：上线时发现"测试时好好的"是因为"测试用的是假文字"。

**Q6**：这些反模式之所以流行，正是因为传统 CSS 无法精确控制文本与容器的关系——设计师用圆角阴影卡片来"包装"内容的不确定性（你不知道文字会溢出多少，所以给一个圆角卡片兜底），用通用推荐区块来"填满"无法精确排版的空间。Pretext 赋予了对文本的精确控制——你知道每个文字块的确切尺寸，可以用精确的间距和层级替代模糊的"卡片式包装"，用精确排版的数据展示替代"通用推荐区块"。有了精确排版能力，装饰性圆角卡片和通用区块就变成了不必要的设计遮盖，而非设计需要。

（5/6 通过）
