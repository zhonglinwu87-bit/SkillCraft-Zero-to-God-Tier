# L6-06：开发者体验评审 —— 让你的API和工具好用到让人上瘾

> 🎯 **学什么**：API 好不好用？CLI 是否直观？SDK 是否一致？用 STOP 方法（Setup/Task/Ongoing/Pain）和 Time to Hello World 评估你的产品给开发者带来的体验。核心洞察：(1) "差的 DX 是无声的杀手——开发者不会投诉，他们只是默默地不用了"；(2) Time to Hello World 可能是 DX 最重要的指标——理想 < 5 分钟，危险 > 30 分钟；(3) API 命名不一致是最常见的 DX 杀手——如果你的 API 创建用 POST /products 但删除用 DELETE /remove-product，开发者每次都要查文档。
> 💡 **难易度**：⭐⭐⭐ | ⏱️ **预计时间**：35 分钟

***

> [!quote]- 📖 原Skill精要
> **技能名称**：plan-devex-review
> **核心功能**：交互式开发者体验计划评审。探索开发者角色、对标竞争对手、设计魔法时刻、追踪摩擦点后评分。三种模式：DX 扩展、DX 打磨、DX 分诊。
> **所属体系**：gstack 虚拟工程团队
> **协作关系**：受益于 [[L6-01-创业门诊室|office-hours]] 的前置诊断，专门针对面向开发者的产品（API、CLI、SDK、平台）

## 1. 课程概览

> 💡 **白话小课堂**：DX（Developer Experience）就是开发者的"使用感受"。传统评审关注终端用户，DX 评审关注开发者用户——好的 DX 意味着更快的集成、更少的支持工单、更高的留存。差的 DX 是无声的杀手——开发者不会投诉，他们只是默默地不用了。

---

## 2. DX 评审的独特价值

```markdown
## Why Developer Experience Review?

产品有两种用户：终端用户 和 开发者用户。

传统评审关注终端用户 → plan-design-review
DX 评审关注开发者用户 → plan-devex-review

好的 DX 意味着：
  → 更快的集成（分钟级而非天级）
  → 更少的支持工单
  → 更高的留存（开发者不会忍受糟糕的 DX）
  → 更多的有机传播（开发者会推荐好用的工具）

差的 DX 是无声的杀手——开发者不会投诉，他们只是默默地不用了。
```

---

## 3. 评审维度

```markdown
## Review Dimensions

### Time to Hello World
从下载到第一个有意义的输出需要多长时间？
  → 理想：< 5 分钟
  → 可接受：< 15 分钟
  → 危险：> 30 分钟

### API 设计
  → 命名是否一致？（createX, deleteX, listX 而非 makeX, rmX, getXs）
  → 参数是否直观？（必填在前，可选在后）
  → 错误信息是否可操作？（不只说"出错了"，说"出了什么错、怎么修"）

### SDK/CLI 体验
  → 安装是否简单？（一行命令 vs 多步配置）
  → 是否有自动补全？
  → 是否有清晰的 --help 输出？

### 文档
  → 快速入门是否存在且有效？
  → API 参考是否完整？
  → 是否有常见场景的代码示例？

### 错误处理
  → 错误是否有类型化的异常？
  → 错误消息是否包含足够上下文？
  → 是否区分了"用户错误"和"系统错误"？
```

> ⚠️ **避坑指南**：API 命名不一致是最常见的 DX 杀手。如果你的 API 里创建商品用 `POST /products`，但删除商品用 `DELETE /remove-product`，开发者每次都要查文档——这不是笨，是你的 API 在浪费他们的时间。

## 4. DX 评审框架

```markdown
## DX Review Framework

### STOP 方法
  S - Setup：安装和配置体验
  T - Task：完成第一个任务
  O - Ongoing：日常使用体验
  P - Pain：出错时的体验

### DX 名人堂
优秀的 DX 示例值得记录和传播。
当遇到特别好的 DX 设计时，记录到 dx-hall-of-fame.md。
这些案例成为未来设计决策的参考。

### 开发者旅程映射
  发现 → 评估 → 安装 → 首次使用 → 日常使用 → 遇到问题 → 升级
  每个阶段的摩擦点是什么？
  每个阶段的惊喜点是什么？
```

> 🔑 **核心秘诀**："Time to Hello World"可能是 DX 最重要的指标。

## 6. 结构拆解：开发者体验评审 Skill 模板

```markdown
## 开发者体验评审型 Skill 模板

### 核心特征
→ 管理对象 = 面向开发者的产品体验（API/CLI/SDK/平台）
→ 核心原则 = STOP 方法 + Time to Hello World + 开发者旅程映射
→ 关键设计 = 五维度评审 + 三种 DX 模式 + DX 名人堂积累

### 通用结构

## Five Review Dimensions（五个评审维度）
- Time to Hello World：<5min 理想 / <15min 可接受 / >30min 危险
- API Design：命名一致、参数直观、错误可操作
- SDK/CLI Experience：安装简单、自动补全、--help 清晰
- Documentation：快速入门可运行、API 参考完整、代码示例
- Error Handling：类型化异常、足够上下文、用户错误 vs 系统错误

## STOP Method（STOP 方法）
- S - Setup：安装和配置体验
- T - Task：完成第一个任务
- O - Ongoing：日常使用体验
- P - Pain：出错时的体验

## Developer Journey Map（开发者旅程）
- 发现 → 评估 → 安装 → 首次使用 → 日常使用 → 遇到问题 → 升级
- 每个阶段识别摩擦点和惊喜点
```

## 7. 电商案例：DX 评审——电商开放平台 API

> 🛒 **实战案例**：一家电商SaaS公司（服务5万商家）准备开放API平台，让第三方ISV和商家技术团队可以集成订单管理、商品上下架、库存同步能力。API设计团队完成了v3版API文档和SDK（Node.js / Python / Java），目标6个月内吸引500个开发者入驻。

> plan-devex-review从STOP四维框架穿透评审：
> - **Time to Hello World实测**：从打开文档站到调用第一个API创建商品——步骤链：注册账号→上传营业执照→等待人工审核（1-3个工作日）→获取API Key→读文档→npm install→写第一段代码→成功创建商品。TTHW评级：>30分钟=危险。根本阻塞点在"人工审核营业执照"——一个想试用的开发者需要等1天才能写第一行代码。改善方案：提供Sandbox模式（注册后立即配发临时API Key，每天限100次调用、100个商品），curl一键示例可复制粘贴运行，TTHW从1.5天压缩到3分钟。
> - **API命名一致性审查**：扫描全部47个端点发现7处不一致——`GET /products/list`（冗余，应为`GET /products`）、`PATCH /product/{id}/update`（单复数不一致+冗余，应为`PATCH /products/{id}`）、`DELETE /remove-product`（动词前置，应为`DELETE /products/{id}`）。错误码更混乱——商品不存在返回404+"not found"纯文本，订单不存在返回400+`{"error":"order_missing"}`JSON，用户认证失败返回401+HTML（Nginx默认页）。标准应统一为`{"code":"RESOURCE_NOT_FOUND","resource":"order","id":"xxx","doc_url":"..."}`的JSON schema。一致性评分：3.5/10。
> - **SDK设计审查**：Node.js SDK的client.products.create()参数名在三个方法间不一致——create用`title`、update用`name`、search用`product_name`（均指商品标题）。Python SDK错误处理逻辑不统一——50%的方法抛异常、50%返回`{error: ...}`。Java SDK需要30行配置才能初始化（Stripe同类只需1行`Stripe.apiKey = "..."`）。SDK评分：4/10。
> - **文档审查**：快速入门中的代码示例用了`"your-api-key-here"`伪占位符——开发者复制后运行直接报错，尚未体验就受挫。改善：文档站为每个访问者预配一个临时Sandbox Key（以Cookie形式注入示例代码），保证首个示例零修改即可运行。

> **STOP综合评分**：Setup 2/10（审核等1天）→ Task 4/10（代码不能直接用）→ Ongoing 5/10（命名不一致每次查文档）→ Pain 1/10（错误返回三种格式）。总评分：3/10=差。修复后目标：Sandbox免审+P0一致性修复+TTHW（TTHW：上手时间指标）<5分钟，开发者注册到首调成功率从当前的23%提升到65%以上。

> 🔑 **启示**：API设计最容易犯的错误不是功能缺失——而是认知负荷。开发者第一次调用失败时不会反省"是不是我理解错了"，而是"这个API太难用了我换一家"。首5分钟的体验决定了一个API平台的生死。

## 8. 掌握检验

**Q1**：Time to Hello World 的"危险"标准是什么？
- A) < 5 分钟
- B) < 15 分钟
- C) < 30 分钟
- D) > 30 分钟

**Q2**：在 STOP 方法中，"P"代表什么？
- A) Performance（性能）
- B) Pain（出错时的体验）
- C) Platform（平台）
- D) Process（流程）

**Q3**：以下哪个 API 端点完全符合 RESTful 命名一致性原则？
- A) POST /products + PATCH /product/{id}/update + DELETE /remove-product
- B) POST /products + PATCH /products/{id} + DELETE /products/{id} + GET /products
- C) POST /create-product + PUT /update-product + GET /products/list
- D) POST /api/v1/product + DELETE /api/v1/product/remove/{id}

**Q4**：在电商 API 案例中，为什么"API Key 需要审核 1 个工作日"是最致命的 DX 问题？请用开发者旅程映射的框架分析。

**Q5**：在 STOP 方法评估中，电商 API 的 S（Setup）得了 2/10 分。如果让你重新设计 Setup 流程，除了 Sandbox 免审核，还能做哪两个改进？

**Q6**："差的 DX 是无声的杀手——开发者不会投诉，他们只是默默地不用了。"结合 STOP 方法分析：在哪个阶段开发者最可能"默默离开"？为什么产品经理往往感知不到 DX 问题？

---

## 9. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**D** —— > 30 分钟即判定为"危险"。

**Q2**：**B** —— STOP = Setup、Task、Ongoing、Pain。

**Q3**：**B** —— RESTful 要求：统一使用复数资源名、HTTP 方法表达操作语义、无冗余路径段。

**Q4**：在"评估"阶段——开发者在看文档，想试一下你的 API 是否适合集成。发现需要审核 1 个工作日，立即形成"这个平台很重"的评价。在"首次使用"阶段——即使等了一天拿到 Key，热情已经消退 90%，而且这期间的竞品可能已经让他完成了第一个集成。TTHW 长达 1 天意味着你的产品在"试用-决定"最关键的窗口期败给了竞品。

**Q5**：两个改进：①提供一键 curl 命令——在文档页嵌入一个完整可用的 curl 示例（含真实 Sandbox Key），让开发者复制粘贴 5 秒内拿到第一个 API 响应；②提供交互式 API 控制台（类似 Swagger UI）——开发者无需安装任何东西，在浏览器中直接调用 API。

**Q6**：最可能默默离开的阶段是 Task（首次任务）——开发者已经完成了安装配置，对"用一下试试"有期待。如果第一个任务遇到障碍，他不会提交 Issue 或发邮件投诉——因为他还没投入足够的沉没成本让你值得他花时间反馈。PM 感知不到的原因是：这些"非用户"从不会出现在支持工单系统、NPS 调查或用户访谈中——他们无声地流失了，没有任何痕迹。

（5/6 通过）
</details>
