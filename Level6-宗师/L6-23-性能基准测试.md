# L6-23：性能基准测试 —— 确保你的代码没有越跑越慢

> 🎯 **学 gstack 的性能回归检测系统**：不是手动打开 Chrome DevTools 看几个指标，而是通过 browse daemon 的 `perf` 命令自动收集 TTFB/FCP/LCP/DOM 等关键指标——与基线对比、检测回归、检查性能预算、追踪趋势——把性能从"感觉慢了"变成"数据说了算"。
> ⏱️ **预计时间**：30 分钟

***

> [!quote]- 📖 原Skill精要
> **技能名称**：benchmark
> **核心功能**：使用 browse daemon 进行性能回归检测。为页面加载时间、Core Web Vitals 和资源大小建立基线。在每个 PR 上进行前后对比，追踪性能趋势。把性能从"感觉慢了"变成可量化、可对比、可追踪的数据。
> **所属体系**：gstack 虚拟工程团队
> **协作关系**：利用 [[L6-37-浏览器自动化|browse]] daemon 的 `perf` 命令自动收集性能指标

## §1 课程概览

benchmark 将性能从主观感受变为可量化的工程数据。它通过 browse daemon 的 `perf` 命令自动收集 TTFB、FCP、LCP、DOM 等关键指标，使用中位数（而非平均值）平抑网络波动。九阶段流程覆盖从环境准备到趋势持久化的完整链路。核心能力包括三部分：基线对比（当前 vs main 分支的性能差异）、回归检测（按小/中/严重三级阈值判定）、性能预算检查（TTFB < 200ms、FCP < 1.8s 等行业标准）。趋势分析将单次数据点扩展为 IMPROVING/STABLE/DEGRADING/VOLATILE 四类趋势判断。与 /health、/qa 共同构成 CI/CD 的三层质量门禁。

> [!tip] 白话小课堂
> 你有没有遇到过"代码没改什么但页面突然变慢了"？benchmark 就是解决这个的——它像汽车的里程表，每次 PR 都自动测一遍性能，和上次对比。慢了就告警，快了就放心。让性能从"我感觉"变成"数据显示"。

## §2 Benchmark 解决什么问题？

```markdown
## "感觉慢了"不是工程数据

传统性能评估：
  → "这个页面加载有点慢"——多慢？
  → "比上一版快了一些"——快了多少？
  → "应该没问题"——应该？凭什么？

gstack benchmark 把性能变成可量化、可对比、可追踪的数据：

  → 每次部署前后自动收集性能指标
  → 与基线对比——回归还是改进？
  → 检查性能预算——超出预警线了吗？
  → 追踪趋势——性能在改善还是恶化？
```

> 💡 **白话小课堂**：你有没有遇到过这种情况——你觉得自己的代码没改什么，但用户突然投诉"页面变慢了"。

## §3 九阶段性能检测流程

```markdown
## Phase 1: Setup（环境准备）
  → 确认 browse daemon 正在运行
  → browse daemon 是性能数据的来源——通过 `perf` 命令
  → 检测无法连接时的回退策略（用户手动提供指标）
  → 确定目标 URL（从 PR / 部署配置 / 用户指定）

## Phase 2: Page Discovery（页面发现）
  → 从项目中提取需要测试的页面列表：
  → 路由文件（routes.rb / app-routing.module.ts / urls.py）
  → 站点地图（sitemap.xml / sitemap.json）
  → 用户指定的页面列表
  → 三类页面：关键路径（必测） / 代表页面（抽样） / 重页面（高风险）

## Phase 3: Data Collection（数据收集）
  → browse daemon perf 命令收集每个页面的指标
  → 多次收集（3-5 次）取中位数——平抑网络波动
  → 收集的核心指标：
    → TTFB (Time to First Byte)：服务器响应时间
    → FCP (First Contentful Paint)：首次内容绘制
    → LCP (Largest Contentful Paint)：最大内容绘制
    → DOM Content Loaded：DOM 构建完成时间
    → DOM Interactive：可交互时间
    → Total Load：完全加载时间

## Phase 4: Baseline Capture（基线捕获）
  → 基准分支（main）的相同页面性能数据
  → 如果不存在 → 收集并存储为基线
  → 基线存储：~/.gstack/projects/$SLUG/benchmarks/<page>.json
  → 基线是后续所有对比的参考点

## Phase 5: Comparison（对比分析）
  → 逐页面对比当前分支 vs 基线
  → 计算每个指标的差异：
    → 绝对值变化（ms）
    → 百分比变化（%）
    → 方向（↑ 变慢 / ↓ 变快）

## Phase 6: Slowest Resources（最慢资源分析）
  → 识别每个页面加载最慢的资源
  → JS bundle / CSS / 图片 / 字体 / API 调用
  → 排序——哪些资源贡献了最多的加载时间？
  → 帮助定位性能瓶颈的具体来源

## Phase 7: Budget Check（预算检查）
  → 对比预设的性能预算：
    → TTFB < 200ms（优秀）/ 600ms（可接受）
    → FCP < 1.8s（优秀）/ 3.0s（可接受）
    → LCP < 2.5s（优秀）/ 4.0s（可接受）
    → Total Load < 3.0s（优秀）/ 5.0s（可接受）
  → 超出预算 → WARNING 标记
  → 超出基线 20% → REGRESSION 标记

## Phase 8: Trend Analysis（趋势分析）
  → 读取历史基准测试数据
  → 绘制趋势线（每个指标的移动方向）
  → 识别趋势：
    → IMPROVING：最近 N 次持续改善
    → STABLE：波动在 5% 以内
    → DEGRADING：最近 N 次持续恶化
    → VOLATILE：无明确方向的大幅波动

## Phase 9: Save（持久化）
  → 保存本次结果到基线存储
  → 更新趋势数据
  → 生成性能报告（markdown）
  → 写入 gstack-review-log（与审查系统关联）
```

## §4 关键性能指标解读

```markdown
## TTFB（Time to First Byte）
  测量：浏览器发送请求到收到服务器第一个字节的时间
  反映了：服务器处理速度 + 网络延迟
  回归原因：慢查询、阻塞的中间件、服务器资源不足
  排查方向：服务端代码、数据库查询、缓存命中率

## FCP（First Contentful Paint）
  测量：浏览器首次渲染任何内容（文字/图片/Canvas）的时间
  反映了：关键渲染路径的效率
  回归原因：阻塞的 JS/CSS、大 HTML、慢字体加载
  排查方向：关键资源大小、渲染阻塞资源、字体策略

## LCP（Largest Contentful Paint）
  测量：视口中最大内容元素完全渲染的时间
  反映了：用户感知的"页面加载完成"时间
  回归原因：大 Hero 图片、慢字体、客户端渲染过慢
  排查方向：最大可见元素的加载路径、图片优化

## 中位数 vs 平均值
  → benchmark 使用中位数而非平均值
  → 中位数不受极端异常值影响（一次网络故障不会污染数据）
  → 多次收集（3-5 次）后取中位数

## 指标之间的关系
  → TTFB << FCP << LCP << Total Load（通常，但不总是）
  → 正常顺序：服务器 → 首次渲染 → 主要内容 → 完全加载
  → 如果 FCP 接近 TTFB → 服务器渲染好，客户端快
  → 如果 FCP 远超 TTFB → 客户端有瓶颈（大 JS bundle）
```

> 🔑 **核心秘诀**：TTFB、FCP、LCP 这三者的时间差是你定位性能瓶颈的"快诊法"。

## §5 回归检测与性能预算

```markdown
## 什么是性能回归？

性能回归 = 代码变更导致性能显著恶化。

## 回归阈值

| 指标 | 小回归 | 中等回归 | 严重回归 |
|------|-------|---------|---------|
| TTFB | +50ms | +100ms | +200ms |
| FCP | +300ms | +600ms | +1000ms |
| LCP | +400ms | +800ms | +1200ms |
| Total Load | +500ms | +1000ms | +2000ms |

## 性能预算——硬性上限

```
PAGE: /dashboard
  TTFB: budget=200ms, actual=187ms ✓
  FCP:  budget=1800ms, actual=2100ms ✗ OVER BUDGET
  LCP:  budget=2500ms, actual=2400ms ✓
  Load: budget=3000ms, actual=3400ms ✗ OVER BUDGET
```

预算检查的逻辑：
  → 任一指标超出预算 → WARNING
  → 两个或以上超出预算 → BLOCK（对 /ship 的建议）
  → 超出预算 + 回归 → CRITICAL（强烈建议优化后再合）

## 预算的来源
  → 行业标准（Google Web Vitals 阈值）
  → 项目历史数据（上次大版本的实际值）
  → 用户指定（项目配置文件）
  → 默认值（上述"可接受"标准）
```

> ⚠️ **避坑指南**： 很多团队犯的错误是"性能预算设得太宽松"——把预算设在"当前值 + 10%"，这样一来任何正常的波动都不会触发告警，预算形同虚设。正确的做法是：预算应该设在"用户开始感知到慢"的阈值，而不是"我们目前的值"。

## §6 趋势分析——不只是看一次

```markdown
## 为什么需要趋势？

单点数据的问题：
  → 一次慢可能是网络波动
  → 一次快可能是缓存命中
  → 单次数据的信号太弱

趋势分析的价值：
  → 连续 3 次恶化 → 不是巧合，是趋势
  → 连续 5 次改善 → 优化有效果
  → 持续稳定 → 当前架构在目标范围内

## 趋势分类

```
IMPROVING ↑
  [95ms] [90ms] [87ms] [84ms] [81ms]
  → 持续改善，方向明确

STABLE →
  [100ms] [102ms] [98ms] [101ms] [99ms]
  → 正常波动范围内，无方向性

DEGRADING ↓
  [100ms] [108ms] [115ms] [122ms] [130ms]
  → 持续恶化，需要干预

VOLATILE ~
  [100ms] [150ms] [80ms] [140ms] [90ms]
  → 大幅波动无规律，可能有外部因素
```

## 趋势告警
  → DEGRADING 趋势 + 最近一次超出预算 → CRITICAL
  → DEGRADING 趋势但仍在预算内 → WARNING
  → VOLATILE 趋势 → INFO（建议调查波动源）
```

## §7 Bench 与 CI/CD 集成

```markdown
## 在 CI 中的位置

/benchmark 适合在以下时机运行：

### Pre-merge（合入前）
  → PR 提交 → CI 触发 → /benchmark 运行
  → 发现回归 → PR 被标记 → 开发者收到通知
  → 无回归 → 合入门禁通过

### Post-deploy（部署后）
  → 部署完成 → /benchmark 在生产环境运行
  → 与部署前基线对比 → 验证生产性能
  → 有时候 staging 的性能不代表生产（不同的基础设施）

### Scheduled（定期）
  → 每日/每周自动运行 → 积累趋势数据
  → 不需要代码变更触发
  → 监控基础设施层面的退化

## 与其他门禁的关系
  → /health：代码结构质量
  → /qa：测试质量
  → /benchmark：运行时性能
  → 三个门禁覆盖质量的不同维度
```

## §8 结构拆解

```markdown
## benchmark 结构模板

### 核心特征
- **管理对象**: 页面加载性能指标（TTFB、FCP、LCP、Total Load）与历史趋势
- **核心原则**: 中位数平抑波动——多次收集（3-5 次）取中位数而非平均值
- **关键设计**: 基线对比 + 三级回归阈值 + 性能预算硬上限 + 四类趋势判断

### 通用结构
- **环境准备层** (Phase 1-2): browse daemon 确认 → 页面发现（关键路径/代表页面/重页面）
- **数据收集层** (Phase 3-4): perf 命令多次收集 → 中位数计算 → 基线捕获与存储
- **对比分析层** (Phase 5-7): 逐页面对比 → 最慢资源分析 → 预算检查 → 回归标记
- **趋势持久层** (Phase 8-9): 历史趋势分析（IMPROVING/STABLE/DEGRADING/VOLATILE）→ 保存 → 报告生成
- **CI 集成点**: Pre-merge（PR 门禁）/ Post-deploy（生产验证）/ Scheduled（定期积累趋势）
```


## §8.5 电商 Skill 案例：电商App首页加载性能持续优化

> 🛒 **实战案例**：某电商App的首页是流量入口（日均UV 50万），但产品团队反馈"首页加载越来越慢"——从半年前的"秒开"到最近的"转圈3-4秒"。工程团队怀疑是陆续添加的新组件（视频Hero、个性化推荐、直播入口等）累积造成的性能退化，但无数据支撑。使用`/benchmark`建立性能基准+持续监控+回归检测体系。

> - **首次基准捕获**：`/benchmark`在staging环境运行——选择3个页面（首页/商品列表页/商品详情页），每页3次收集取中位数。首页性能——TTFB 180ms、FCP 0.8s、LCP 4.2s(⚠️超过2.5s预算68%)、Total Load 6.8s。最慢资源分析——Hero视频背景(5.2MB .mp4, load time 2.1s/占LCP的50%)、推荐商品组件API响应(P99 820ms)、第三方直播SDK初始化(600ms阻塞渲染)、个性化推荐脚本(480ms解析)。性能预算设定——LCP < 2.5s(硬上限)、FCP < 1.0s(硬上限)、Total Load < 4.0s(软上限)。
> - **优化措施与迭代**：Round 1——Hero视频→静态WebP图片+CSS动画效果（文件大小5.2MB→380KB, -93%），LCP从4.2s→2.1s(-50%)。Round 2——推荐组件API添加CDN边缘缓存(TTL 5min, P99从820ms→95ms, -88%)。Round 3——直播SDK改为懒加载（用户滚动到"直播"section时才初始化，首屏渲染延迟600ms→0ms）。Round 4——推荐脚本使用`<script defer>`异步加载（不阻塞首屏渲染）。四轮优化后——LCP 4.2s→2.1s→1.5s→1.5s→0.98s(-77%)、FCP 0.8s→0.5s→0.5s→0.4s→0.4s(-50%)、Total Load 6.8s→4.5s→3.2s→2.8s→2.1s(-69%)。
> - **持续监控与回归检测**：`/benchmark`设为每周自动运行（Scheduled模式）→每次收集3页面的性能指标与历史基线对比。第6周检测到LCP从0.98s→1.6s(+63%回归)→触发WARNING→自动分析最慢资源→发现新增的"双11预热弹窗"(800KB PNG背景图未压缩)→团队压缩图片到120KB WebP→LCP恢复到1.0s。回归检测阈值——>30%回归=FAIL阻断部署、10-30%=WARN需评估、<10%=PASS。3个月运行数据——性能趋势IMPROVING（LCP: 4.2→0.98→稳定在1.0-1.2区间），期间检测到2次性能回归（均在部署前拦截修复）。

> 🔑 **启示**：性能优化的最大挑战不是"做一次优化"——是"确保不会退化回来"。团队在2周内把LCP从4.2s优化到0.98s是值得庆祝的，但如果没有持续监控，3个月后新加入的弹窗组件可能在无人感知的情况下把LCP拉回到3s。"感觉慢了"总是比"实际慢了"滞后3-6个月——benchmark让性能退化在发生的当下就被检测到，而非在产品经理抱怨后才开始排查。

> [!info] 参考来源
> 性能基准测试与回归检测参考了 [Web Vitals](https://web.dev/vitals/) 标准、[Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) 的性能门禁模式和 [SpeedCurve](https://www.speedcurve.com/) 的持续性能监控方法论。

## §9 掌握检验

**Q1**：如果 TTFB 很低（50ms）但 LCP 非常高（4500ms），性能瓶颈最可能在哪里？
- A) 服务器端的数据库查询
- B) 客户端的渲染阻塞（大 JS bundle / 大 Hero 图片）
- C) 网络延迟
- D) DNS 解析

**Q2**：性能回归检测中，"中等回归"的 FCP 阈值是多少？
- A) +300ms
- B) +600ms
- C) +1000ms
- D) +200ms

**Q3**：为什么 benchmark 使用中位数而非平均值？请给出一个具体的数值示例：5 次测量 [100ms, 105ms, 98ms, 102ms, 2500ms]，中位数和平均值各是多少？哪个更能代表"典型用户体验"？

**Q4**："超出预算但无回归"和"在预算内但持续恶化"哪个更需要关注？请从用户体验和工程策略两个角度分析——并说明在什么条件下，第一个场景比第二个场景更紧急。

**Q5**：趋势分析中 VOLATILE 趋势（大幅波动无规律）的可能原因有哪些？如果一个关键页面的 LCP 呈现 VOLATILE，你的排查优先级是什么？

**Q6**：性能预算的设计原则是"预算应设在用户感知到慢的阈值而非当前值+10%"。如果你的 LCP 当前是 4.5s，预算设在 4.0s 意味着什么？这种"预算先于现状"的策略在工程上都遇到了哪些阻力？如何说服团队？

***

## §10 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** —— TTFB 低说明服务器响应快、网络好。

**Q2**：**B** —— 回归阈值：小回归 +300ms、中等回归 +600ms、严重回归 +1000ms。

**Q3**：平均值 = (100+105+98+102+2500)/5 = 581ms；中位数 = 102ms。这个示例清楚展示了平均值的欺骗性——一次网络抖动（2500ms）让平均值变成 581ms，让人觉得页面很慢，但实际上 80% 的用户体验是 98-105ms。中位数（102ms）才是典型用户体验的正确代表。中位数对异常值免疫——这正是 bench 选择中位数的统计原理。

**Q4**："在预算内但持续恶化"更需要关注——因为它代表系统性退化。超出预算但无回归 = 一开始就慢（可能是设计权衡或基础设施限制），是已知的、被接受的债务。持续恶化 = 在你不注意的时候系统正在腐烂——每条 PR 都在悄悄增加 50ms。用户体验角度：从 2.5s 稳定变到 3.8s 比一直 4.2s 更让用户不满——因为用户记得"以前是快的"。紧急例外：如果预算设在关键业务阈值（如 Google 开始惩罚高于 2.5s 的页面），"超出预算"的即时业务影响（搜索排名下降）> "持续恶化"的渐进影响。

**Q5**：可能原因：①CDN 缓存命中率不稳定（回源 vs 边缘节点差异大）；②第三方脚本加载时间不可控（广告、分析工具的外部服务器响应波动）；③数据库连接池在不同时间段的争用程度不同；④后端定时任务（如每小时的数据汇总）周期性消耗资源。排查优先级：先确认是否是外部因素（第三方脚本、CDN）→ 如果是，考虑异步加载或超时兜底；再检查是否有定时任务与测试时间窗口重合 → 如果有，错开测试窗口；最后检查自身服务的资源争用模式。

**Q6**：预算 4.0s 说明团队承认"当前的 4.5s 是不可接受的用户体验"，预算不是对现状的确认而是对目标的承诺。阻力：①"产品都跑了一年了用户没投诉"——用户不投诉不代表满意，可能是"忍了"或"不知道可以更快"，Google 数据显示 LCP 从 4.5s 降到 2.5s 能提升 15-20% 的转化率；②"现在没有资源做性能优化"——预算不是"必须立即达标"，而是"不能比现在更差"，先把底线守住，再逐步优化接近目标。说服团队：把预算设为目标而非现状，相当于"不许再胖"——有人还在吃但至少不许再吃了。

（5/6 通过）
</details>
