# L7-07：分布式数据一致性 —— 钱和库存永远对得上的工程方法

> 🎯 **学分布式系统中的数据一致性工程**：不是"最终一致性"四个字糊弄过去，而是从 ACID 到 BASE、从 CAP 定理的工程含义、幂等性设计、Saga/TCC 补偿事务（Saga（先做后补：执行操作→失败则补偿）/ TCC（Try-Confirm-Cancel：先锁后做：预留资源→确认执行→取消释放））、到对账修复的完整数据保障体系。
> ⏱️ **预计时间**：50 分钟

***

> [!tip] 💡 白话小课堂
> 分布式系统里，"数据一致"不是一件天然的事——你在订单库里存了100元，支付库里可能记成99.99元，库存那边可能显示已卖出10件但仓库只有8件。数据一致性的本质是：在多个独立数据库之间，如何保证"同一个事实"被所有人正确记录。不是选"要一致性还是要可用性"——是给每个具体操作选"这个操作能容忍多大延迟和不一致"。

> [!warning] ⚠️ 避坑指南
> CAP定理最大的误解：以为是"三选二"。真相是P（网络分区）不是可选的——网络一定会有问题。真正的选择只是：发生网络问题时，你要一致性还是可用性？支付选C（宁可不可用也不能扣错钱），推荐选A（推荐不太准也比什么都没有好）。同一个系统的不同API可以做不同选择——这比"整个系统选CP或AP"重要得多。

> [!info] 🔑 核心秘诀
> 幂等性是分布式系统的第一原则——"至少一次投递+幂等消费=恰好一次效果"。四种实现方式：唯一幂等键（UUID存结果）、业务唯一约束（订单号唯一）、版本号乐观锁（UPDATE SET version=version+1 WHERE version=old_version）、状态机约束（只允许合法状态流转）。选哪种？简单场景用业务唯一约束，复杂场景用幂等键表。

## 1. CAP 定理的工程含义——不是选两个

```markdown
## CAP 不是"三选二"

常见的误解："微服务只能选 CP 或 AP"

### CAP 定理的正确理解

在网络分区（P）发生时，你必须选择 C 或 A：
  → P 不是可选的——网络分区必然发生
  → 所以真正的选择是：发生网络分区时，选一致性还是可用性？

### 电商系统中不同场景的 CAP 选择

> 📐 **选择原则**：资金正确性 > 订单正确性 > 用户体验连续性 > 分析数据准确性。一句话——**涉及钱的选 CP，涉及体验的选 AP**。

| 场景 | 选择 | 理由 |
|------|------|------|
| 支付扣款 | CP | 一致性优先——没扣款不能说扣了 |
| 库存扣减 | CP | 超卖比不可用更严重 |
| 商品浏览 | AP | 可用性优先——看到旧价格比看不到好 |
| 购物车 | AP | 暂时不一致可以接受 |
| 订单创建 | CP | 订单号不能重复，金额不能错 |
| 推荐系统 | AP | 推荐不太准比没推荐好 |
| 积分系统 | AP | 积分延迟到账可以接受 |

### 关键工程洞察
  不是"整个系统选 C 或 A"
  而是"每个操作选 C 或 A"
  同一个服务内的不同 API 可以做不同选择
```

## 2. 幂等性——分布式系统的第一原则

````markdown
## 幂等性是分布式系统的基础

### 为什么幂等性是第一原则？
  在分布式系统中，"最多一次"和"至少一次"的语义都有问题：
    → 最多一次（at-most-once）：消息可能丢失 → 订单丢失
    → 至少一次（at-least-once）：消息可能重复 → 重复扣款
    → 解决方案：使用 at-least-once 投递 + 幂等性消费 = 恰好一次

### 幂等性实现模式

**模式 1：唯一键（Idempotency Key）**
  客户端生成 UUID → 服务端存储：
  
  ```sql
  CREATE TABLE idempotency_keys (
    key VARCHAR(36) PRIMARY KEY,
    response JSONB,
    created_at TIMESTAMP DEFAULT NOW()
  );
  
  -- 处理请求时
  INSERT INTO idempotency_keys (key, response) VALUES ($1, $2)
  ON CONFLICT (key) DO UPDATE SET updated_at = NOW()
  RETURNING response;
  ```

**模式 2：业务唯一约束**
  不需要额外的幂等键表：
  → 订单：(order_id) UNIQUE
  → 支付：(out_trade_no) UNIQUE → 重复通知自动忽略
  → 退款：(refund_id) UNIQUE

**模式 3：版本号（乐观锁）**
  每次修改带版本号：
  ```sql
  UPDATE inventory 
  SET available = available - 1, version = version + 1
  WHERE sku = $1 AND version = $2;
  
  -- 如果 affected_rows = 0 → 版本冲突 → 重试或失败
  ```

**模式 4：状态机约束**
  只允许合法的状态转换：
  → PENDING → PAID ✓
  → PENDING → CANCELLED ✓
  → PAID → PENDING ✗（非法转换，拒绝）
````

## 3. Saga 补偿事务——分布式事务的工程实践

````markdown
## Saga 模式详解

### 传统分布式事务（XA/2PC）为什么不适用？
  → 需要数据库支持 XA 协议（锁资源直到所有参与者确认）
  → 锁定期间其他事务无法访问 → 并发性能断崖
  → 协调者单点故障 → 整个系统被锁死
  → 不适合微服务的异构数据库环境

### Saga 的核心思想
  把一个长事务拆成多个本地事务 + 补偿操作：

  正向流程：
    T1: 创建订单 → 成功
    T2: 扣减库存 → 成功
    T3: 扣款 → 失败（余额不足）
  
  补偿流程（逆序执行）：
    C2: 释放库存 ← 补偿 T2
    C1: 取消订单 ← 补偿 T1

### Saga 的两种实现

**Choreography（编排式）**：
  服务之间通过事件通信，每个服务知道自己的补偿：
  
  Order Service → OrderCreated
    → Inventory Service 消费 → 扣库存 → StockDeducted
      → Payment Service 消费 → 扣款 → PaymentFailed
        → Inventory Service 消费 → 释放库存
  
  优点：简单，无中心协调者
  缺点：流程分散在多个服务中，难以监控和理解

**Orchestration（协调式）**：
  一个 Saga Orchestrator 管理整个流程：
  
  Saga Orchestrator:
    1. → 调用 Order Service 创建订单
    2. → 调用 Inventory Service 扣减库存
    3. → 调用 Payment Service 扣款
    4. → 如果第 3 步失败 → 依次调用补偿
  
  优点：流程集中管理，易于监控和修改
  缺点：Orchestrator 成为新的单点（需要高可用设计）

### 电商的 Saga 实践
  简单流程 → Choreography（订单取消 → 释放库存 → 释放优惠券）
  复杂流程 → Orchestration（大促凑单：创建订单 → 扣库存 → 计算满减 → 分摊优惠 → 扣款）
````

## 4. 对账系统——最后一道防线

```markdown
## 没有对账的系统是在裸奔

### 对账的三个层次

**Layer 1: 实时校验（秒级）**
  → 关键操作写完后立即读回验证
  → 订单创建 → 3 秒后查询确认 → 不一致告警
  → 支付扣款 → 查询支付网关状态确认

**Layer 2: 定时对账（分钟/小时级）**
  → 库存对账：Redis vs DB vs WMS（仓库系统）
  → 每 5 分钟扫描差异 → 自动修复 + 告警
  → 支付对账：已支付订单 vs 已发货订单（防止漏发货）

**Layer 3: 每日全量对账（T+1）**
  → 支付网关对账单 vs 平台支付记录
  → 逐笔比对 → 差异分析
  → 自动修复 + 修复失败 → 人工工单

### 对账系统的架构

```
每日对账流程：

1. 获取对账单
   → 下载支付网关 T+1 对账单（CSV）
   → 解析 → 标准化为统一格式

2. 逐笔比对
   → 按 out_trade_no 匹配
   → 四类差异：
     ✓ 一致：双方记录一致
     ⚠ 平台独有：我方有记录，网关无（可能被风控拦截）
     ⚠ 网关独有：网关有记录，我方无（未记录的交易）
     ⚠ 金额差异：双方都有但金额不一致

3. 自动修复
   → 平台独有超过 24h → 自动取消订单 + 退款
   → 网关独有 → 补录订单（可能是回调丢失）
   → 金额差异 → 人工工单

4. 对账报告
   → 总交易数、总金额、差异数、差异金额
   → 修复成功数、修复失败数
   → 趋势：日/周/月的差异率变化

## 5. 电商案例：订单状态与库存扣减的分布式事务一致性

> 🛒 **实战案例**：某电商平台在微服务拆分后遇到了经典的分布式事务难题——订单服务与库存服务分属两个独立数据库，"创建订单→扣减库存"这个在单体中一条ACID事务完成的操作，现在需要跨服务协调。一天高峰期，订单创建成功但库存扣减失败的场景发生了37次：用户看到"下单成功"但15分钟后收到"库存不足已取消"的短信——NPS从42骤降到18。
>
> **用 gstack 架构体系实现分布式一致性**：
> 1. /plan-eng-review 评审方案 → 对比三种模式：XA/2PC（锁资源直到所有参与者确认→实测并发性能断崖：P99从50ms→4.2s）、TCC Try-Confirm-Cancel（先锁后做→预留库存→确认扣减→取消释放→实现复杂但隔离性好）、Saga（先做后补→本地事务逐个执行→任一步失败则逆序补偿→实现简单但中间态可见）。结论：下单场景选Saga Choreography（事件编排式）
> 2. /review 审查Saga实现代码 → 发现2个CRITICAL：(1)补偿操作的幂等性缺失——StockReleased事件重放时会重复INCR库存→导致库存虚增→修复：补偿事件也带idempotency_key；(2)正向操作成功但补偿操作失败时的死信处理缺失——库存已扣但退款发起失败→订单永远卡在中间态→修复：补偿失败进入死信队列+人工工单+24小时超时自动重试
> 3. /qa 构建分布式事务测试 → 模拟5000笔订单，随机注入3种故障：订单创建后库存扣减失败(5%)、库存扣减后支付失败(8%)、支付成功后物流创建失败(3%)→验证所有场景的补偿完整性和最终一致性→5000笔全部正确结算，0差异
> 4. 设计对账系统三层防御：Layer 1实时校验（订单创建3秒后RPC查询库存确认扣减成功→不一致立即补偿）、Layer 2定时对账（每5分钟扫描订单状态=PAID但库存状态≠DEDUCTED的差异→自动修复）、Layer 3每日全量对账（T+1日逐笔比对订单表和库存流水表→发现累积偏差→生成差异报告）
>
> **效果**：
> - "下单成功但库存不足"的异常从日均37笔降至0笔（Saga补偿100%覆盖）
> - 补偿操作成功率：正常路径99.2%，死信队列人工处理0.8%（日均约2笔需人工介入）
> - P99延迟：Saga模式320ms vs XA/2PC方案4.2s（并发性能提升13倍）
> - 每日全量对账差异率从0.15%降至<0.001%（三层防御的叠加效果）
> - Saga流程可视化：任意一笔订单可查看完整的事件链（OrderCreated→StockReserved→StockDeducted→PaymentCompleted→OrderConfirmed→OrderShipped→OrderDelivered→SettlementTriggered）及每一步的补偿状态
>
> > 🔑 **启示**：分布式事务不能追求ACID的完美，但必须追求"可修复性"——不是"永远不会不一致"，而是"不一致一定能在设定时间内被发现和修复"。Saga的正向操作与补偿操作必须成对设计——每定义一个T_N都要同时定义C_N，且C_N必须幂等（补偿的补偿=空操作）。最重要的工程原则：CAP不是在系统级别选的——支付选CP（不一致比不可用更严重），推荐选AP（推荐不太准比没推荐好），同一个订单系统下单选CP、购物车选AP——每个API端点独立决策。

## 7. 掌握检验

**Q1**：CAP 定理在工程中最常见的误解是"三选二"。正确的工程理解是什么？
- A) 分布式系统必须在一致性和可用性中全局二选一
- B) P（网络分区）不是可选的——网络一定会有问题。真正的选择是：发生网络分区时，这个具体操作选一致性还是可用性。同一个系统内的不同 API 可以不同选择（支付选 CP，推荐选 AP）
- C) 只要网络不出问题，就能同时保证 C 和 A
- D) CAP 定理已经过时，现代系统可以同时满足三者

**Q2**："至少一次投递 + 幂等消费 = 恰好一次效果"——这是分布式系统的第一原则。请列出 4 种幂等性实现模式，为每种模式写出一个具体的电商场景代码示例（伪代码即可），并指出每种模式最适合什么场景。

**Q3**：Saga 和传统 XA/2PC 在锁资源的方式上有本质区别。以下哪个场景描述准确地揭示了这种区别？
- A) Saga 和 2PC 都会在事务期间锁定所有资源
- B) 2PC 在第一阶段（Prepare）锁定所有参与者的资源直到所有确认（可能数秒甚至更久），Saga 的每个本地事务立即提交释放锁——这是 Saga 并发性能优于 2PC 的核心原因，但代价是放弃了自动回滚（需要手动补偿）
- C) Saga 比 2PC 更安全，因为它保证了一致性
- D) 2PC 不需要锁资源

## 8. 答案

<details>
<summary>点击查看答案</summary>

**Q1**：**B** — CAP 定理的 P（网络分区）是必然发生的——交换机故障、网络拥塞、DNS 故障、云服务商网络问题。当网络分区发生时，必须在 C 和 A 之间选择。不同场景不同选择：支付扣款选 CP（不一致比不可用更严重——少收钱=财务损失，多收钱=监管风险），推荐系统选 AP（推荐不太准比没推荐好），商品浏览选 AP（看到旧价格比看不到好）。关键洞察：不是整个系统打一个标签——是每个操作（甚至每个 API 端点）做独立选择。

**Q2**：模式 1 唯一幂等键：`INSERT INTO idempotency_keys (key, response) VALUES ($1, $2) ON CONFLICT (key) DO UPDATE SET updated_at = NOW() RETURNING response`——适用支付扣款（最安全，显式幂等表）。模式 2 业务唯一约束：`INSERT INTO orders (order_id, ...) VALUES ($1, ...)` 依赖 order_id UNIQUE 约束——适用订单创建（业务主键天然唯一）。模式 3 版本号乐观锁：`UPDATE inventory SET available = available - 1, version = version + 1 WHERE sku = $1 AND version = $2`，如果 affected_rows = 0 则版本冲突重试——适用库存扣减（无额外存储）。模式 4 状态机约束：只允许 PENDING→PAID，拒绝 PAID→PENDING——适用订单状态流转（利用状态本身的单向性）。

**Q3**：**B** — 2PC 的 Prepare 阶段向所有参与者发出"准备提交"请求，每个参与者锁定相关资源并返回"准备好"——在此期间资源对其他事务不可用。如果协调者在收到所有确认后崩溃，锁可能被一直持有直到人工介入。Saga 将长事务拆分为多个独立的本地事务（ACID 在单库范围内），每个本地事务完成后立即提交释放锁，下一个 Saga 步骤使用新的事务。锁的持有时间从"整个分布式事务的持续时间"缩短为"每个本地事务的持续时间"，这就是 Saga 的并发性能优势。代价：没有自动回滚——需要显式的补偿操作，且补偿也可能失败（需要补偿的补偿）。

**Q4**：Layer 1 实时校验（秒级）：关键操作写完后立即读回验证——如订单创建后 3 秒查询确认——发现秒级不一致立即告警。Layer 2 定时对账（分钟/小时级）：每 5 分钟扫描 Redis vs DB vs WMS 差异——发现分钟级累积偏差。Layer 3 每日全量对账（T+1）：支付网关对账单 vs 平台支付记录逐笔比对——发现最隐蔽的差异（如回调丢失导致平台无记录但网关已扣款）。"裸奔"的含义：如果前面所有实时防护（幂等性、签名验证、双路径、状态机）都失效——比如某个 bug 导致某些订单未被记录——T+1 对账是绝对的最后防线，逐笔比对会发现"网关有交易但我方无记录"的差异。没有对账意味着没有任何机制发现已经发生的错误。

**Q5**：状态机定义：PENDING→PAID（条件：收到支付成功回调且签名验证通过），PENDING→EXPIRED（条件：超过 15 分钟未支付且 Timer 触发），PAID→REFUNDING（条件：用户申请退款且退款金额<=原支付金额），REFUNDING→REFUNDED（条件：收到退款成功回调），REFUNDING→REFUND_FAILED（条件：退款被拒）。幂等性保证：每个转换的触发事件带 event_id，状态机验证"当前状态可以从 X 转换到 Y"，合法→执行转换，非法→幂等返回（如果当前已经是目标状态→直接返回成功，如果是非法的源状态→拒绝并告警）。如：当前状态=REFUNDED，收到 PaymentCompleted 事件→状态机拒绝（已退款订单不能被标记为已支付）→告警并调查。

**Q6**：正确顺序（近→远）：(b) OOM 修复——从源头消除根因；(c) 回调先写 Kafka——即使应用崩溃，回调事件持久化在 Kafka 中，重启后重新消费；(a) 主动查询——最终兜底。如果 OOM 再次发生（修复不完全）且 Kafka 消费也失败（消费者 offset 提交异常），主动查询 Worker 每 30s 轮询过去 5 分钟内所有 PENDING 状态支付→查到微信返回 SUCCESS→补录。最坏情况：一笔支付成功后最多等待 5 分钟（主动查询窗口）才能被修复。这种纵深防御思路与 L7-03 库存系统的五层超卖防护和 L7-04 支付系统的双路径设计异曲同工——核心哲学：永远不依赖单一机制保证正确性。
